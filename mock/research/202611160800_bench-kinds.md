# Snapshot and tracking benches

Until now a bench was one thing to the harness. Some benches in the consumer trees are microbenchmarks whose arms are written once and kept as a reference, and some build against the crates of the repository they sit in and are rerun as that code changes. The harness read the history of both the same way, so a timing that moved was called a regression whether the code had moved or the machine had, and nothing stopped a reference bench from quietly taking a dependency on living code and turning into something else under its own history.

The intent this answers, in op's words: "We need a few explicit and separate concepts on the bench side: snapshot benches, as in, intentionally isolated code that stays as is forever as a reference and static bench setup. Then tracking benches, that have and or use living actual code for the benches, which is a more valuable one in some sense. That separation is harness concern upstream that you'll do. With that, it's more clear what each bench intents and how it should work and how the data should be approached and analysed." The intent is the separation and that each kind carries its own contract for building and for reading its data. Everything below is the vehicle chosen for it.

## The dividing line

A dependency is inside when it is a `path` into the bench tree (`<mock>/benches/`), and outside otherwise: a path out of the tree, a git source, a registry crate, a dependency inherited from a workspace. A snapshot builds only from inside; a tracking bench reaches outside at least once. The two are exhaustive and exclusive, so every bench is exactly one of them and the kind its reach admits can be computed, which is what makes the migration total.

The line sits at the tree and not at the repository on purpose. A git dependency pinned by `rev` and a registry crate pinned by `=` look frozen, but their own dependencies still resolve on every build, since an arm is a workspace of its own and no lockfile of it is committed. Freezing them would need the whole resolved graph frozen, which a manifest cannot state. So a snapshot vendors what it needs into the tree, and anything that can move under it is living code by definition. The harness's own crates, `mockspace-bench-*`, are the instrument and not the code measured, and are passed over.

What is read to decide it: `[dependencies]`, `[build-dependencies]` and their `[target.*]` forms, `[patch.*]`, the `[lib] path`, and in Rust source the literal paths of `include!`, `include_str!`, `include_bytes!` and `#[path = "..."]`. A path built with `env!` or `concat!` is not resolvable by a lint and is not read; that is the one gap the check has, and it is stated where the check is.

## Snapshot

A snapshot is isolated reference code and a static setup. Its arms build only from inside the bench tree, and `mock bench freeze <bench>` writes `<bench>/snapshot.lock`, one line per file it builds from with its sha256: the arm crates, every in-tree crate they reach, any in-tree file their source includes, and the bench's own `bench.toml`, so the setup is frozen with the code. A bench declared as a `[bench.<name>]` section locks into `<name>.snapshot.lock` beside the file declaring it. Build output (`target/`), dot directories and an arm's `Cargo.lock` are not part of it.

The files never change after. The lint refuses a snapshot whose files differ from its lock, naming each file changed, new or gone, and `freeze` refuses to rewrite a lock its files no longer match. Changed reference code is a new snapshot beside the old one. A shared support crate a snapshot reaches is frozen with it, which is the honest consequence of sharing: editing it for another bench's sake changes the reference. To keep that from happening by accident, an arm whose manifest the tool generates takes only its own bench's `support/` when the bench is a snapshot; a snapshot that wants a root `support/` crate names it in a manifest of its own, which puts it under the lock in plain view.

Its data is read as a reference. A run records the lock's id (the first twelve hex digits of the lock file's digest) in the `source` column of its `summary.tsv`, and every arm of it stands at that one source. The code is fixed, so a timing that leaves its point says the machine, the toolchain or the harness moved, and the run reports it as `DRIFT`. How points are read is the same for both kinds, below under "Source and system as variant axes".

## Tracking

A tracking bench builds against living code, at least one arm reaching outside the bench tree, the repository's own crates in the usual case. It has no lock, and the lint refuses one beside it. A tracking bench whose arms reach nothing outside is refused too: nothing its history follows can change, so it is a snapshot without the lock that would keep it one.

Its data is read along its source points. Each arm's summary rows carry the arm's own source, a digest of the code it built from, so a run is identified by what it measured rather than by the commit it was taken at. The first version of this work read tracking history by clean commits and never flagged a run on a dirty tree; the amendment below replaced that, since the source names the code exactly, uncommitted edits included.

## Declaring it, and what refuses

Every bench declares `kind = "snapshot"` or `kind = "tracking"`: a composed bench at the top of its `bench.toml`, a section inside its `[bench.<name>]`. Sweeps inherit it and may not declare one, since two sweeps read two ways would be two benches. A bench that declares none is refused, three times over: by the lint `a-bench-keeps-the-contract-of-its-kind` at the commit gate, by `mock bench run` and `report` before they build anything, asking the same predicate, and by the harness when it loads the tree. A word that names no kind is refused at parse. A snapshot with no lock is refused by the harness when its run config is built, since the run could not say which code it measured. `bench_matrix!` takes a required `kind:` and writes it into every section it generates, because which kind a matrix is depends on what its carrier crate reaches.

No kind is defaulted. A default would make every existing bench silently one kind and read its history that way, which is the confusion the separation is there to end.

## Migration

`mock bench migrate --kinds [--dry-run]` writes into every bench that declares no kind the one its reach admits, prepended as the first line of a composed bench's file and inserted into a section's table, says why for each, and then freezes the snapshots it declared. It was run against a copy of hilavitkutin's bench tree: 30 benches came out as snapshots (the atomic, branch, bounds-check and strategy microbenchmarks among them, including the ones sharing root support crates such as `kernel_checks` and `rsb-kernels`), and 12 as tracking, each naming its reach: `engine_vs_std`, `frame_wide` and `single-trunk-convergence` through `evs-support` into `crates/hilavitkutin*`, the swap and wake benches through `rcm_common`, and `fiber_theory`, `rcm_order` and `rcm_rivals` through `notko` on a git branch. Every consumer migrates with the one command and commits the result; a bench that should be the other kind is then made so by changing what it builds from, which the lint checks.

## What else changed

The summary schema gains two columns, `source` and `system`, as `schema_v2`; a row written before them parses with both empty, and a reader takes its system from the run's machine class directory. The `[benchspace]` glob grammar moved into `mockspace-bench-layout` so the harness and the lint pack resolve members with one copy of it. The builtin benches rule and the `benchmarking` skill describe both kinds, `freeze`, `migrate --kinds` and the axes.

## Source and system as variant axes

Op amended the work twice. His words, verbatim:

"Tue source hash should perhaps be considered a variant in the tracking benches. This way the data isn't  swinging heavily on the impl, and we can easiely see which points in time made it faster or slower etc. unless that's where it is already. And I'd say that each target system that runs the shit should also be considered a variant, which I think it already might be technically but not thoroughly and not in the analysis or comparisons"

"Oh we want the benches to gather results as much as they get for old hashes/revs too etc. it should not avoid adding more data. We want all the data."

The intent: the source a tracking run measured is a variant axis, so results group by it and the trail of points shows which change made it faster or slower; the system that ran a bench is a variant axis everywhere the data is read, never pooled; and grouping is for reading only, never a reason to collect less. The hedges ("perhaps", "unless that's where it is already", "which I think it already might be") are kept for provenance and are not open questions.

What was built:

- One abstraction, `mockspace_bench_harness::axes`. An `Axis` trait with three implementations, `Variant`, `System` and `Source`, and every reading of history goes through it: `on::<A>` and `split::<A>` select and group rows by one axis, `trail` gives a variant's source points on one system in the order its runs visited them, `step` says whether one point is slower, faster or level against the one before (intervals that do not overlap), and `standing` reads a run against its history. Both kinds are read the same way; a snapshot simply has one source.
- A row's point is its variant, its system and its source. Every run adds a row to its point, whatever commit it was taken at, an older one included, and a source the code returns to after another gathers its new rows with its old ones. A run at the point its history already stands at is read for `DRIFT`, since the code did not move; a run at a new point is read against the point just before it, `REGRESSION` where its interval lies wholly above and `FASTER` where it lies wholly below. The dirty-tree rule of the first version is gone: the source names the code, so a dirty tree is measured and read like any other.
- A tracking arm's source is taken by `mock bench run` once the arm is built: the digest of every file the arm builds from, followed out of the bench tree through every crate it takes by path (out of the tree a crate is read as cargo builds it, its manifest, its build script and `src/`; its tests are not part of an arm), named relative to the bench tree with `..` so every checkout of the same files reads the same, and of `name version source` for every package the arm's lockfile resolved from git or a registry, the harness's own crates left out. A moved git branch and a newer registry release are therefore new points, which closes the earlier gap that the resolution was not recorded. The tool hands the driver one `<library path prefix>\t<source>` line per arm in `MOCKSPACE_BENCH_SOURCES`; the driver maps each library to the name it exports at preflight and writes the source into that variant's rows.
- A row's system is the machine class, and after it, `+`-joined, `target=<triple>` for a cross target and each `target-cpu=` and `target-feature=` codegen flag the driver was handed in `CARGO_BUILD_TARGET`, `RUSTFLAGS` or `CARGO_ENCODED_RUSTFLAGS`. Flags set in a cargo configuration file are not read; that is the predicate's limit. History was already read per machine class directory; it is now split by the system column as well, so two builds on one machine for two targets are two variants.
- The audit of every reading path: the driver's regression check (now `axes::standing`, per variant and system), the run's terminal summary and report (the report opens with kind, system and how to read it), `results/INDEX.md` (each cell shows its systems side by side, one column each by its latest run, and every system's trail of points with its steps, before the per-machine sections), and the generated `BENCHES.md` (the same two tables per cell, and one section per system rather than per machine class). The per-run analysis in `report.rs`, `summary.rs` and the detectors reads one run's samples, which are one system by construction, so nothing there pools systems. `meta_report.rs` correlates variant families across benchmark CSVs it is handed by path and has no caller in the tool; it pools whatever it is handed, and is left as it is.
- Nothing in the harness skips, deduplicates or refuses a run because results already exist for its point, revision or system: each run is its own run directory, never replaced, and every row of every run is read back. The one place a run's rows are withheld is an `after_cell` hook returning `Fail`, which is the consumer's verdict on that run and not about existing data.
- Running a tracking bench against an older revision of its living code is not cheap to add: the arms reach the living crates by path, so the run needs a worktree of that revision for the crates while keeping the current bench tree and promoting into its results. The harness already files such a run under that revision's point; the checkout half is ticket `run_a_tracking_bench_at_an_older_revision_of_its_living_code`.

Tests carry the case that must fail for each: a row on another system is not read against this one's history while the same row on its own system is; every run at a source adds to its point; a run at an older source lands under that point again; a move at the same point is drift and at a new point is the code's; a new point is read against the point just before it, not against older ones pooled; the views keep systems in their own columns and trails; a build pointed at a target is another system; a tracking arm's code follows its path dependencies out of the tree, reads the same in another checkout, is moved by a source change two crates out and not by a test file; a source moves with a moved branch or release and not with the instrument; and end to end, four runs of a tracking bench (twice unchanged, once with the living crate edited, once with it put back) are all written, the first, second and fourth at one source, and `INDEX.md` shows that point gathering its three runs.

## Left

- The driver and the hooks library are outside both contracts: they are the instrument's side, built from the tree's `src/lib.rs` and every support crate, and neither kind constrains them.
- The self-bench under `benches/` in this repository is a runner of its own built on `BenchManifest::load` and is declared tracking, since what it exists to follow is the living harness; it is a candidate for deletion in favour of the end-to-end tests, which cover the same pipeline through the generated driver.

- Running at an older revision, as said above, is a ticket.
- A system's target flags set in a cargo configuration file are not read into the system.
