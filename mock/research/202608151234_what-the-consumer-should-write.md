# What the consumer should write

An independent read of the bench framework's ergonomics, dispatched to answer one
question: what should a person authoring a benchmark actually have to say, and
where should they say it. The evidence is the four consumer trees as they stand,
read but not written to, and the framework source at `dev`. A separate expert is
establishing what the matrix machinery is and where configuration currently
lives; this file does not duplicate that and disagrees with it nowhere it
overlaps, because the overlap was checked.

Gate outcome first, because it changes how the rest should be read. **There is no
`mock/canon/` in this repository**, so there is no ratified canon to defend and
no canon this work can conflict with. The governing material is the maintainer's
own stated doubt, quoted in the brief, plus the shipped code. The two redesign
documents on `docs/bench-ergonomics-survey` are agent output with no recorded
human decision, so they are tested here rather than built on. Where this file
agrees with them, that is corroboration only to the extent that both were derived
from the same source independently, which is stated case by case below.

The one-sentence answer: the maintainer's instinct is right, sweeps do carry a
lot of configuration, and the measurement missed it because **the measurement
counted keys in a file that is, for the largest consumer, generated output**. The
configuration lives in three places at once, and the fix is not to move it from
code into config but to stop asking for it two of the three times.

## 1. The recollection is correct, and the machinery already exists

The maintainer's recollection: "it started as the timed matrix where there are
several sensors in one bench setup kind of. And the matrix runs the different
configs of that one bench with different things plugged in."

That is accurate, and it is not a memory of a plan. It is a description of code
that shipped. `bench-harness/src/matrix.rs:3-6` opens:

> A composition bench sweeps several axes (dispatch shape, record layout, value
> representation, program profile, ...) and needs one variant cdylib crate per
> point in the cartesian product, each wrapping the right library function with
> `#[bench_variant]`, plus a `bench.toml` section wiring the variants together.

"Several sensors in one bench setup" is `MatrixSpec.axes`. "Different things
plugged in" is `AxisValue`. The layer above it, `bench-matrix`, narrows that to
the shape consumers actually wanted: one family, one axis of cells, one outer
sweep. `bench-matrix/src/decl.rs:57-61` defines it under the maintainer's own
later word:

```rust
/// The outer family sweep: one bench per value.
pub struct SweepAxis { pub name: String, pub values: Vec<String> }
```

So the rename did not come from nowhere and it did not come from the redesign.
`SweepAxis` entered with the semantic-matrix layer (commit `2471643`, the crate's
first commit), and it means one axis whose values each produce one bench section.
The redesign's `sweep` means one axis instantiation inside a bench, which lands
at the same granularity: one sweep value, one `[bench.*]` section today. The two
usages agree. That is worth saying plainly, because the vocabulary section of the
redesign proposes `sweep` as a new word, and it is not new; it is the existing
word being extended from "values of one axis" to "independently named axes", which
is a generalisation the evidence supports. arvo's `warm-container-width-l1`,
`width-l2`, `density-w13` are not values of one axis. They are different axes.
`SweepAxis` cannot express them and `[sweep.<name>]` can.

**Keeping the word is the right call and the redesign should be more confident
about it than it is.** It presents `sweep` as the new word that dissolves the
shared-arm problem. It is the old word, already in the tree, already meaning this,
and that is a stronger position.

## 2. The measurement counted a generated file

The measurement the maintainer is doubting says that of roughly 240 future
sweeps, two carry anything beyond a point list and an arm list, and it counted
keys in `bench.toml`.

For vehje, the largest consumer, `bench.toml` is 4955 lines and **270 of its 337
`[bench.*]` sections sit below this line**, at `vehje/mock/benches/bench.toml:1068`:

```
# >>> bench_matrix (generated by mockspace-bench-matrix)
```

Everything below that marker is rewritten wholesale on every generator run.
`bench-matrix/src/generate.rs:126-133`:

```rust
let base = match existing.split_once(MARKER) {
    Some((before, _)) => before.trim_end().to_string(),
    None => existing.trim_end().to_string(),
};
let body = format!("{base}\n\n{MARKER}\n{}\n", sections.join("\n"));
std::fs::write(&toml_path, body)
```

So for 80 percent of vehje's sections, nobody chose those keys. They are the
projection of a `bench_matrix!` block through `to_spec` (`generate.rs:55-97`),
which emits exactly `title`, `carrier_dep`, `extra_deps`, `master_seed`, `sizes`,
`baseline_contains`, `normalise_mode`, `floor_contains`, `name_template`,
`lib_template` and the axis values, and nothing else, because nothing else is in
the struct. Counting keys there and concluding that a sweep needs little
configuration is measuring the width of a funnel's spout.

What the author of one of those sections actually wrote is
`vehje/mock/benches/carrier/src/bench/dispatch.rs:21-53`, thirty-three lines
carrying a name, a crate path, a crate dependency line, a seed, a sweep axis with
six values, a point list, a baseline, a floor, a regime, a typed setup function,
and eight cells one of which is feature-gated. That is a great deal more than a
point list and an arm list, and it produced 6 sections and 30 measured cells.

The honest restatement of the measurement is: **a generated `bench.toml` section
carries almost no configuration, because the configuration was consumed upstream
in the generator input.** That is a fact about the lowering, and it says nothing
about how much a person has to write. The maintainer's suspicion that the config
"now lives in the code instead of the config file" is correct for the matrix
consumers, and for them it is correct by design rather than by accident: the
`bench_matrix!` block is code because half of what it carries is code, and the
half that is not came along for the ride.

## 3. What arvo's 672 lines actually are

The brief asks, per construct: written because the framework required it, because
the config file could not express it, or because it genuinely belongs in code.
Reading `arvo/mock/benches/src/main.rs` end to end, there are four categories, not
three, and the fourth is the one that matters most.

**Category one, the framework required it and no longer does.** Lines 16 to 201
(the manifest loop, the section filter, the report-only branch, the csv and report
paths) and lines 597 to 672 (the worker). That is roughly 250 of the 672 lines,
and `mockspace_bench_harness::driver::drive` subsumes all of it. This is not a
finding about what people needed; it is a finding that arvo never migrated. arvo
tracks `branch = "dev"` (`arvo/mock/benches/Cargo.toml:27-28`), so `drive` has
been available to it the whole time. kirjo, on the same branch, is 60 lines
because it calls `drive` (`kirjo/mock/benches/src/main.rs:52`). vehje is 51 lines
for the same reason. **Any argument that reads arvo's line count as evidence of
consumer need is reading an unmigrated tree.**

**Category two, configuration wearing code's clothes.** The workload block, lines
50 to 53, is four lines naming two stage constructors. Every consumer has one
(`kirjo:16-42`, `hilavitkutin:193-206`, `vehje:17-30`) and every one of them is a
list of the six harness stage constructors with integer arguments. This is a table
of names and integers and it belongs in config. The redesign says so and is right.

hilavitkutin has the purest specimen, at `hilavitkutin/mock/benches/src/main.rs:213-216`:
a thirteen-name `matches!` list deciding `may_differ`. That is a per-bench boolean
flag, the manifest has a key for it, and I verified the drift: **all thirteen
names exist as `[bench.*]` sections and the manifest contains zero `may_differ`
keys.** A property of a bench is recorded in a Rust match arm, in a different
file, in a different crate, from the thing it describes. This is exactly the
"table of names" the redesign's premise targets, and the premise is correct here.

**Category three, code that is genuinely code.** The routine table, lines 206 to
595. Section 4 opens this up, because it is neither purely config nor purely
code and the redesign treats it as the former.

**Category four, and this is the one to notice: written because the framework did
not do it.** These lines are not configuration and not domain code. They are a
consumer patching the harness from outside, and they are all commented in the
first person about a defect. Lines 25 to 30 add a `--bench` filter because without
one "a dispatch measuring one thing destroys the artifact trail of all the
others". Lines 134 to 144 call `harness::validate` because "`harness::run` does
NOT do this", with a note that a one-character off-by-one "produced 400 rows of
ordinary-looking numbers and exit 0". Lines 150 to 160 call
`check_disasm_duplicates` because "nothing in this driver ever called it, so no
bench in this repository has ever been told that two of its arms compile to the
same machine code".

Those three fixes are the most valuable content in the file and every one of them
is a private repair of a shared defect. **A framework whose correctness checks
must be wired by each consumer has already lost them**, and the evidence that it
loses them is that hilavitkutin's driver, 311 lines, wires none of the three.
Nothing in either redesign document lists this as a hook, and it should not be
one: it is the library's job, the library already ships all three functions, and
the only reason arvo has them is that one person read the source. The redesign's
ordering section step 4 does fold validation and disasm into the generated driver,
which is the correct resolution, and it should be stated as a correctness fix
rather than as a step in a sequence.

## 4. The real defect: the same facts are written three times

This is the finding I would put in front of the maintainer first, because it
explains both the 672 lines and why moving configuration around will not fix them.

Take one real bench, `bitpack-carrier-width`. Its point list is six integers. Here
is where those six integers are written.

In the arm crate, `arvo/mock/benches/variants/bitpack-carrier-d16/src/lib.rs:10-14`:

```rust
#[bench_variant(
    CarrierColumn,
    "bitpack-carrier-d16",
    sizes = [16384, 131072, 1048576, 2097152, 4194304, 8388608]
)]
```

In the manifest, as six `[[bench.bitpack-carrier-width.sizes]]` rows, each with
`n` and a six-entry `variants` array.

In the driver, `arvo/mock/benches/src/main.rs:509-514`:

```rust
("bitpack-carrier-width", 16384) => routine_bridge!(CarrierColumn<16384>),
("bitpack-carrier-width", 131072) => routine_bridge!(CarrierColumn<131072>),
("bitpack-carrier-width", 1048576) => routine_bridge!(CarrierColumn<1048576>),
("bitpack-carrier-width", 2097152) => routine_bridge!(CarrierColumn<2097152>),
("bitpack-carrier-width", 4194304) => routine_bridge!(CarrierColumn<4194304>),
("bitpack-carrier-width", 8388608) => routine_bridge!(CarrierColumn<8388608>),
```

Six arm crates repeat the list in their attribute, the manifest holds it once as
six rows, and the driver holds it as six match arms (`p3_output.txt`). **The same six integers are
written thirteen times for one bench**, and the type `CarrierColumn` is written
seven times. Change a point and seven files are wrong, six of them silently: the
arm's dispatch table simply will not have that N, and the failure surfaces as a
load or dispatch error rather than as a diff.

Across arvo the shape holds exactly. The driver's table has **256 live match arms
and the manifest has 256 size rows**, a perfect one to one. And the arms carry
almost no information: grouping them by section shows **47 distinct sections and
47 distinct (section, type) pairs**, so the bridge type is a function of the
section name alone and the point contributes nothing to choosing it. The
warm-container family is the clearest case: **57 match arms, all of them
`routine_bridge!(Case<...>)`, encoding one fact.**

So the 256-arm table is 47 facts plus 209 lines of restatement. That is the number
the ergonomics question turns on.

The reproduction for every count in this section is committed beside this file at
`202608151234_probes/`.

## 5. The sweep-needs-no-config measurement, corrected

The redesign puts a number on it at `design.md:431-432`: a sweep "overrides only
what differs, which the survey measured as rare (257 of 258 sweeps share their
bench's arm set)".

I measured this independently from the manifests and get a different answer,
because there are two different questions hiding in that sentence.

**Do the points within one section share an arm set?** Yes, with exactly one
exception. Parsing arvo's manifest, **1 of 256 size rows carries an arm set
differing from the first row of its own section**, in `bitpack-write-contend-race`,
where `bench_bitpack_write_unsound` is dropped at four points because it disagreed
with the ground truth on 2 of 100 validation seeds there. So the per-point
override is needed, once, for a good reason, and **the redesign is right to keep
it** (`design.md:432`).

That "1 of 256" is almost certainly what the 257-of-258 figure measured, and on
its own terms it is very nearly correct. The error is that a measurement of
**rows within a section** is quoted in support of a claim about **sweeps within a
bench**, which is the next question and has a different answer.

**Do the sweeps within one bench share an arm set?** No, frequently not. Grouping
arvo's 49 sections into benches by shared arms reproduces the redesign's structure
exactly and independently (**7 families, 11 singletons, 36 shared arms**, matching
`design.md:28-40`), and then: **13 of the 49 sweeps need an `arms` override** under
a bench-level default, which is 27 percent, not 0.4 percent. Five of the seven
families carry more than one distinct arm set among their members. The
ten-section warm-container family has three.

The redesign's own worked example is right where its prose is wrong: it shows an
`arms` subset override on the second sweep it writes (`design.md:419`). The prose
calls that rare. In arvo it is one sweep in four.

A caution about this measurement, since it is the one that contradicts a shipped
number. My first parse of it was wrong in the flattering direction: it skipped the
four rows carrying a comment between `n` and `variants`, and those four are the
only rows in arvo with a per-point override, so it reported zero and I briefly
wrote that per-point overrides were dead weight. The probe now raises rather than
skipping when a row does not parse. The defect and the fix are recorded at
`202608151234_probes/README.md`, because a probe that excludes the rows able to
falsify it is worth more as a warning than as a deleted mistake.

**This matters for the maintainer's question directly.** He asked whether sweeps
should have a lot of config. On the axis the redesign measured, no. On the axis
that decides the schema, a quarter of them override the arm set, and that is
before `may_differ`, `threaded`, `normalise`, and timing overrides. The
schema needs the override to be first-class and pleasant, not an escape hatch.

## 6. What the consumer should write

For `bitpack-carrier-width`, end to end, in the shape I would ship. Nothing here
uses a mechanism the tree does not already contain; section 7 names the precedent
for each.

The bench directory holds one manifest:

```toml
# mock/benches/bitpack-carrier-width/bench.toml
[bench]
title   = "Packed 13-bit against u16, u32 and u64 dense carriers, L1 to past L2"
routine = "bench_bitpack_carrier_shared::CarrierColumn"
seed    = 0x1234_5678_9ABC_DEF0
arms    = ["d16", "d16-control", "d32", "d64", "packed", "packed-simd"]

[sweep.width]
points = [16384, 131072, 1048576, 2097152, 4194304, 8388608]
```

Ten lines. Each arm is one file with no manifest:

```rust
// mock/benches/bitpack-carrier-width/arms/d16/src/lib.rs
use bench_bitpack_carrier_shared::sum_d16;
use mockspace_bench_core::{timed, FfiBenchCall};

#[bench_arm]
fn run(input: &Input, output: &mut Output) -> FfiBenchCall {
    timed! { run { output.value = sum_d16(&input.d16, N); } }
}
```

No `sizes` list, because the points are in the manifest and the arm belongs to
exactly one bench. No routine type named, for the same reason. No `Cargo.toml`,
because its every line is derivable: the name is the directory, the crate type is
fixed, the dependency set is the pinned framework crates plus the bench's declared
support crate.

And the consumer writes **no Rust driver at all**. Not a shorter one. None.

The comparison against today, for this one bench: ten manifest lines and six short
files, against roughly fifty manifest lines, six arm crates each with a
sixteen-line `Cargo.toml` and a five-line attribute, six driver match arms, six
workspace member entries, and a share of a 672-line driver binary that must exist
before anything runs.

For arvo whole, the driver goes from 672 lines to zero, and the 47 facts its table
encoded move to one `routine` key per bench manifest.

### The mechanism, and the one place it is load-bearing

The driver crate is generated by the tool, given a path dependency on the
consumer's support crates, and the routine table is emitted into it by
substituting the config's `routine` string and the sweep's points:

```rust
// generated; never hand-edited
("bitpack-carrier-width", 16384) => routine_bridge!(bench_bitpack_carrier_shared::CarrierColumn<16384>),
```

**Why generation rather than a macro, which is the fork the redesign leaves
open.** The redesign proposes a `routine_table!` macro and flags it at
`design.md:518-522` as the one piece nobody compiled. The reason to prefer
generation is not aesthetic and it is decisive: **monomorphisation needs literal
tokens.** `routine_bridge!(T<N>)` requires `N` as a literal in the expansion, and
`macro_rules!` cannot iterate a `const POINTS: &[usize]` to produce one arm per
element. So any Rust-side table, however well factored, **must restate the point
list in Rust**, and the duplication of section 4 survives the refactor. That is
precisely what `byte_routine_dispatch!` does today: it takes `sizes = [...]` as
literals (`bench-core/src/lib.rs:384`) and every consumer hand-copies its manifest's
point union into that call. A macro moves 256 lines to 47 lines plus 256 integers.
Generation moves them to 47 strings in config and nothing in Rust.

The cost, stated honestly: `routine = "..."` puts a Rust path in a config string,
so a typo becomes a compile error in generated code rather than a config
validation error. I would take that trade, because it is the trade `bench-matrix`
already made and shipped: `CellDecl.op_path` and `MatrixDecl.setup_path` are
exactly this, strings that become Rust paths under substitution
(`bench-matrix/src/decl.rs:44-52`, `generate.rs:26-38`). The failure mode is known
and the error names the path. A tool that wants to do better can emit a
`const _: fn() = || { fn assert<T: Routine>() {} assert::<CarrierColumn<16384>>(); };`
alongside, which turns the diagnostic into one naming the config key.

**Where the answer flips.** If a bench's routine cannot be named by a path because
it needs a `where` clause the config cannot carry, or the consumer wants the table
type-checked in its own crate before generation runs, the `routine_for` hook is
the right escape and should stay. It is one function, it exists
(`bench-harness/src/driver/mod.rs:63`), and mockspace's own self-bench uses it. Keep
it; just stop making it the only road. Today 100 percent of arvo's routine
dispatch goes through the hook because there is no alternative; under this shape
the residue would be whatever genuinely resists a path, and my reading of arvo's
fifteen live bridge types is that the residue is zero.

## 7. What the framework should stop asking for

Each of these is currently asked of every consumer, is derivable from what the
consumer already said, and has a shipped precedent for the derivation.

**A driver binary.** `cargo mock bench init` writes one
(`src/bench.rs:511`, `STARTER_BIN_MAIN`) and the consumer owns it forever. kirjo's
copy is that starter, near verbatim, and 42 of its 60 lines are a workload the
config should carry and a `routine_for` that returns `None`. Generating the crate
is proven twice over: `src/custom_lints.rs:93` writes a `Cargo.toml` plus
`src/lib.rs`, builds it and dlopens it, and `bench-matrix` writes crates that call
consumer code by path.

**A point list in the arm.** `#[bench_variant(..., sizes = [...])]` is the same
list as the manifest's, in a file that belongs to exactly one bench. The generator
already substitutes it in the matrix path (`generate.rs:43-52` renders
`sizes_literal` into the attribute), which proves the direction: the manifest is
the source and the attribute is downstream. Extend that to hand-written arms and
the third copy disappears.

**A per-arm `Cargo.toml`.** Sixteen lines of which the name is the directory, the
crate type is always `cdylib`, and the dependencies are the pinned framework plus
the bench's support crate. arvo has 94 of these. vehje has 902, of which 594 are
already generated. The redesign proposes generating them with the hand-written
manifest as an escape hatch, which is right.

**A workload program.** Four blocks across four consumers, all compositions of six
constructors with integer arguments, two of them identical
(`hilavitkutin:195-204` and `vehje:19-28`).

**The correctness checks.** Validation, the disasm duplicate check, the artifact
filter. arvo wires them by hand and hilavitkutin does not, so hilavitkutin's
numbers have never been cross-checked between arms. This is not ergonomics; it is
a correctness defect wearing an ergonomics costume, and it is the strongest single
argument for the driver being the tool's.

## 8. Where I disagree with the redesign

The design is largely sound and its family analysis reproduced independently under
my own parse, which is real corroboration rather than agreement by reading. Four
disagreements, marked defect or taste.

**Defect. The vehje migration cannot be a `git mv`.** `design.md:469` proposes
"scripted `git mv` of 902 arms under their benches" and lists `bench-matrix` as
unchanged (`design.md:485-486`). Those cannot both hold. 594 of vehje's 902 arms
are generated (`bench-matrix` writes them at `bench-harness/src/matrix.rs:319`,
`out_dir.join("variants").join(&v.name)`), the emitted manifest paths are
hardcoded to `variants/{0}/target/release/{0}`
(`matrix.rs:270` and `matrix.rs:301`), and `generate_all` rewrites every section
below the marker on the next run (`generate.rs:126-133`). Moving generated output
by hand produces a tree the generator restores to the old shape on its next
invocation. Either `bench-matrix` emits the new layout, in which case it is
changed and belongs in the migration plan, or vehje cannot migrate. This is
recoverable and cheap to fix in the plan, and it needs fixing before anyone
scripts it.

**Defect. The 257-of-258 figure does not support the claim it is attached to.**
Section 5 above. The correct arvo figure at sweep granularity is 13 of 49, and the
schema decision (whether an arm override is an ordinary thing or an escape hatch)
rests on it.

**Defect, minor and worth correcting because both numbers are cited as evidence.**
`design.md:271` and `design.md:330` call it "arvo's 360-arm table". It is 256 live
arms plus 2 commented out, in lines 206 to 595, a 390-line function.
`design.md:403` says the warm-container family costs "66 driver match arms". It is
57. Neither error changes a conclusion; both should be fixed so a later reader
does not inherit them.

**Taste, and I would go further than the design does.** It keeps `routine_for` as
a hook and adds `routine_table!` to make its 256 lines shorter. I would generate
the table and let the hook be the exception, for the monomorphisation reason in
section 6. The design's own expressibility ledger already licenses generating the
byte dispatch from config at generation time (`design.md:508-509`), and it does not
extend that to the typed dispatch. The two are the same emission with a different
type name substituted, so the inconsistency looks like an oversight rather than a
judgement.

One thing the design gets right that is worth defending against a future reviewer:
**splitting `results/` from `history/` at the top level** (`design.md:236-245`) so
that `rm -rf results/` stays safe next to an append-only tracked ledger. That is a
small decision with a real failure mode behind it and it should survive.

## 9. Test-gate observation, outside the question asked

Reported under the standing instruction to name what I notice. The three bench
crates are green, 99 tests. But **`generate_all` has no test**, and it is the
function that rewrites consumer manifests and writes 594 of vehje's arm crates.
Its three neighbours test `sizes_literal`, a template placeholder, and `to_spec`
(`generate.rs:164-194`), all pure functions. Nothing pins what the marker rewrite
preserves, nothing pins that content above the marker survives, and nothing pins
where the crates land. A migration plan that reorganises generated trees is being
written against an untested generator. The cheap fix is a test that writes a
manifest with hand content above the marker and stale content below it, runs
`generate_all`, and asserts both halves.

## 10. What I did not settle

The vehje section count does not reconcile. The manifest has 337 `[bench.*]`
sections (67 authored, 270 generated); the design refers to "vehje's 180 sections"
at `design.md:87` and `design.md:469`. I could not determine what 180 counts, and
did not chase it, because it belongs to the other expert's scope and none of my
conclusions depend on it. It should be reconciled before the migration table is
trusted, since the vehje row is costed against it.

I also did not price the generated-driver build cost. Generating and compiling a
driver crate per run adds a compile to every `mock bench run`, and
`custom_lints.rs` already does this for lints so the cost is knowable, but I did
not measure it and will not guess. If it is material, the mitigation is the same
`write_if_changed` idempotence `custom_lints.rs:146` already uses. That is a
question for the harness, and it is unpriced.
