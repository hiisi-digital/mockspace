# Commit subject gates, surveyed

Op asked what the opt-in conventional-commit checks check and allow and how they are configured, then for gates that block more readily and for a per-project configuration so a new type needs no change to mockspace. His words, 16 November: "Bench: is a good commit category though. But yeah do some snooping on mockspace and see what the opt-in conventional commit lints and checks actually check and allow and how they are configured. Then improve the gates to block more readily and improve configuration so new ones can be added per project etc". The trigger was seven `bench:` commits on hilavitkutin's `dev` that passed the commit-msg gate although `bench` is not in that project's commit-style type list.

This note is the survey, as it stood before the change, and then what the change does. Line references are to the tree at `fb3db6e`.

## Where a commit subject is checked

Three surfaces carry a commit message to a lint, and all three end in the same engine entry, `check-message` (`src/entry/message.rs`).

The `commit-msg` git hook is generated by `gen_commit_msg` in `src/bootstrap/hooks.rs`. It reads the author and committer from `git var`, then runs `check-message --domain commit-message --gate commit --file <msg>`. It fires however the commit is made.

The `pre-push` hook scans every commit being pushed through the same entry with `--batch`, one record per commit, so a commit that skipped the first hook is still judged at the push.

The agent `check-message.sh` hook (`src/render_agent/builtins.rs`) submits the text of a `git commit` or forge command to the same entry with the command attached as an invocation. A lint that wants the subject out of a command line has to parse a shell command, which the shell hook cannot do.

The byline checks are a separate matter and are not about the subject: the old `check-byline.sh` grep is gone and byline policy now arrives through the message lints too, configured under `[attribution]` in `mock/agent/config.toml`. `lib/attribution/` is a review-sweep library and judges nothing at a commit.

## What those surfaces check

The surfaces only carry a message to lints. Before this change mockspace shipped no message lint of its own. `check_message_with_extra` in `lint-rules/src/lib.rs` ran only the lints a pack supplied, its doc comment said a commit convention is not something an engine should impose, and `run` in `src/entry/message.rs` returned success at once when the pack held no message lint. A project that imported no pack with a commit lint had a commit gate that was wired and checked nothing.

The one shape lint that exists is `commit-style` in the separate `mockspace-extra-lints` repository (`src/lints/commit_style.rs`). It checks a type from a configured list, the separator, a breaking marker, a parenthesised scope, subject case, subject length, a trailing period and a blank line after the subject. Every knob defaults to permissive: `types` is empty and `require_type` is false, so an unconfigured `commit-style` accepts every subject. Its own doc comment says so: "a project declares its style, or declares none and this lint does nothing." Two presets in `presets/`, `commit-conventional` and `commit-hiisi`, list the knobs, and the comment in the lint says nothing loads them yet. A project configures the lint by hand under `[lints.commit-style]` in `mockspace.toml`.

The attribution lints in the same pack (`message-attribution`, `forge-body`) judge trailers and identities and say nothing about a subject.

## Where the type list lives

In a consumer the list lives twice and the two copies never meet. Two repositories, arvo and hilavitkutin, carry a hand-written `mock/agent/skills/commit-style/SKILL.md.tmpl` with a fixed list in its text (`feat`, `fix`, `refactor`, `docs`, `test`, `chore` in hilavitkutin), and neither includes `bench`. The others have no commit-style skill at all, and muisti and riimu set `types` under `[lints.commit-style]` for the pack lint. Mockspace shipped no commit-style skill of its own. Nothing connects the skill to the gate, and nothing tells a project to set the second when it writes the first.


## Why `bench:` passed

hilavitkutin imports `mockspace-extra-lints`, so `commit-style` is in its pack, and its `mockspace.toml` holds no `[lints.commit-style]` table (the same is true of arvo and kaski). The lint therefore ran with `types` empty and checked no type. The commit-msg hook invoked it faithfully and it returned nothing, for `bench:` and for every other subject. The skill's list was documentation and enforced nothing.

This was not a gap in the hook, the engine or the lint's logic. It was three things together: the only commit lint lived in a pack, its default was silence, and the project's list was prose.

So the set of types in use differs by project, and every project has drifted past the list its skill states. `bench` is one of several. A fixed list in mockspace would be wrong for all of them, which is the argument for a default that is a floor and a per-project key that extends it.

## Opt-in or not

Opt-in is the gap, in this sense: a gate that exists in every repository and does nothing until a pack is imported and a table written is the state in which seven subjects passed and nobody was told. The default is therefore on. A project that wants no convention sets `commit = "off"` under `[lints.commit-subject]`, which alone turns every gate off, so nothing is imposed that cannot be removed in one line. The cost is real, and it arrives at once: every consumer pins `mockspace_branch = "dev"`, so a change landed on `dev` is taken on the next `cargo mock` in each of them, with no pin to bump. The order of landing is therefore part of the change. Each consumer first lands `[lints.commit-subject] extra_types` covering the types of its last 300 subjects (the lists above), which an older engine only lists as a table matching no lint, and only then does the mockspace branch land. The review of this branch (`review-1.md`) found the first version of this paragraph wrong on that point.


## What the change does

A builtin message lint, `commit-subject` (`lint-rules/src/commit_subject.rs`), runs in every project, ahead of any pack lint, at the commit gate, the push gate and in `mock lints`. `run` no longer returns early for a pack with no message lint. It checks the rules the commit-style skill states and nothing it does not: a type from the configured set, then `: `, a message that starts lowercase, no parenthesised scope, no trailing period, at most 71 characters. The mood of the verb is not checkable and is left alone. A blank line after the subject is available as a knob and is off, because the skill does not state it. Subjects git wrote, in the shapes it writes them (`Merge branch`, `Merge pull request #`, `Revert "`, `Reapply "`), are not held to it, and `fixup!`, `squash!` and `amend!` pass the commit gate and are refused at build and push. Leading blank lines are skipped before the subject is taken. A refusal of an unknown type names `extra_types` and the table to put it in.

It is configured under `[lints.commit-subject]` in `mockspace.toml`, by the same parameter mechanism every lint already has: `extra_types` adds to the default set, `types` replaces it, and `separator`, `breaking_marker`, `require_type`, `max_subject`, `subject_case`, `allow_scope`, `forbid_trailing_period` and `require_blank_line` move the rest. A key the lint does not know and a value it cannot read stop the load of `mockspace.toml` with the line that is wrong. The default set is `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `bench` and `release`, the last for the merge commit `homma release run` writes.

The same parameters render a builtin `commit-style` skill, so the documentation lists exactly the set the gate accepts, and a rule the project has loosened is no longer printed as a rule. A consumer's own `commit-style` template still overrides the builtin and can read the configuration through `{{commit_types}}`, `{{commit_rules}}` and `{{commit_examples}}`. `agent_commit_style_skill = false` declines the builtin.

## Left open

The agent hook still cannot judge a subject, because the engine receives a command and not a message. The git `commit-msg` hook always follows and catches it, so nothing falls through, but the agent sees the refusal at commit time and not at the tool call. Reading a subject out of a shell command belongs in the hook or in a parser in `lint-rules`.

`mockspace-extra-lints` kept its own `commit-style` lint with the same nine knobs, and muisti and riimu configured it. Two implementations of one convention disagreed from the day this change was written (muisti had no `bench` and a limit of 72), so the pack's lint is retired and muisti and riimu move to `[lints.commit-subject]` keeping their sets and limits. The mockspace branch lands after those, and after the two further conditions in the landing order below.


The `no parentheses` line in the workspace skill reads as a rule about parentheses anywhere in a subject, and the lint enforces the narrower shape the existing check had, a parenthesised scope after the type.

## Landing order

Review 2 corrected the order in three places, and this is the order as it stands.

1. Each consumer lands its `[lints.commit-subject]` table first: applets, arvo, hilavitkutin, homma, muisti and riimu. For arvo and hilavitkutin this is the branch `work/commit-subject-types`, which holds the config table and nothing else. An older engine only lists such a table as one matching no lint, so landing it first is safe.
2. The mockspace branch `work/commit-type-gates` lands only after kaski's ticket 78609af5c53e is closed and huurre's table has moved (ticket `huurre_mock_tools_fail_to_build_against_the_current_mockspac`, which has to cover moving huurre's `[lints.commit-style]` table to `[lints.commit-subject]` and not only its seat). Until then huurre's table governs nothing once the pack lint is retired, and the defaults refuse `research` (78 of its last 300 subjects). kaski and huurre have no branch of this change and none is made here.
3. arvo and hilavitkutin then land the template step, `work/commit-subject-config`, which switches their hand-written `SKILL.md.tmpl` to `{{commit_rules}}`, `{{commit_types}}` and `{{commit_examples}}`. An engine older than this branch leaves those three tokens in the text literally, so the step cannot land before the mockspace branch is on `dev`.

The default set carries `release` because `homma release run` merges with `release: <version>` in every repository, and the commit gate and the push scan of `main` would otherwise refuse each release. muisti and riimu replace the defaults with their own `types` list, so each carries `bench` and `release` itself. applets lists `deploy` and `merge` besides its other types, which its history carries from before the 300-commit window.
