## 1. `list_args` dropped `-Ffoo` and the `-Z` flags (8804c1c)
`src/suite/live.rs`: `-Z` is now a valued build flag, and the attached short forms `-F<v>` and `-Z<v>` are kept, so a run-only flag given that way no longer vanishes from the `nextest list` call. Test first, shown failing (`-Fv` listed as `[]`): `every_separated_and_attached_form_of_a_valued_flag_is_listed` (every valued long flag as `--f v` and `--f=v`; `-F`/`-Z` as `-F v`, `-F=v`, `-Fv`) and `an_attached_feature_does_not_swallow_the_word_after_it`. I could not read the #153 review (the API returned no reviews or comments), so the forms come from your brief.

## 2. Per-member opt level (410dabe)
New `[test.opt_level]` table in `mockspace.toml`: member name to `0`..`3`, `"s"` or `"z"` (refused otherwise, naming the member). `cargo mock test` under nextest writes `target/mockspace-test-state/cargo.toml` with `[profile.<p>.package."<member>"] opt-level`, `<p>` being `release` for `--release`/`-r`, the `--cargo-profile` named, else `dev`. It is passed as `--config <file>` to both the `nextest list` and the `nextest run`, before the caller's own flags so theirs win. Members not named keep their manifest's level; a name that is not a member gets a note. Confirmed cargo honours the file (`opt-level=3` / `opt-level=s` in rustc's command line). Tests, each shown failing first: settings (`a_member_carries_its_opt_level`, `an_opt_level_cargo_would_refuse_is_refused_with_its_member`), nextest (`each_member_gets_its_own_opt_level_under_the_profile_built`, `the_profile_built_follows_the_flags_that_choose_it`, `the_run_builds_with_the_generated_cargo_config_before_the_callers_flags`, `no_member_opt_level_means_no_cargo_config`), and end to end `a_members_opt_level_reaches_the_build` (build scripts read `OPT_LEVEL`; the test fails unless the level reached the build; on the old code it fails at config refusal of the unknown key). Docs: `help.rs`, `render_agent/templates.rs` (the rules every consumer generates), `docs/USAGE_GUIDE.md`. `agent_builtin/` has no text on `mock test`'s settings, so it is unchanged. Not done: `--plain` (cargo test) runs do not get the opt level.

## 3. Village nextest config (no code change; #153 closed it)
The refusal is `operator didn't match any binary IDs` on an override naming a binary that is gone from the workspace. Reproduced with cargo-nextest 0.9.148 on the pre-#153 build (`ad523ec`): a heavy test in an example `figure_preview` that the history remembers, then the example deleted, `--full --workspace` fails with that error before running; on the tip it runs green and the history no longer names the test. I added the regression test for kaski's shape, `a_deleted_example_with_a_heavy_test_does_not_stop_the_next_run` (b3fe78e): fails on `ad523ec`, passes on the tip. One thing I could not reproduce: an example that is still declared but not built (`required-features`) is accepted by nextest, so it never was the refusal. What remains: when `nextest list` itself fails, nothing is dropped (#153 prints a note), so a stale binary can still stop that run.
