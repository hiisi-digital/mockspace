# v1 parity audit: mockspace v2 vs the three sibling references

Audit done 2026-05-22 ahead of the next implementation slice. The user's directive: "pay special attention before going to new features, about our feature set matching the existing v1, so we don't lack any features it had. So benches, sketches, research, all these need to be first-class and provided first-party by us in the mockspace ecosystem, too."

The three reference repos for v1 mockspace are:

- `~/Dev/loimu/mock/`: older sibling; principal reference for agent infrastructure (skills, hooks, rules under `agent/`).
- `~/Dev/polka-dots/mock/`: principal reference for the bench harness (`benches/` with bench-core + bench-macro crates, a decade of CSV plus findings outputs).
- `~/Dev/saalis/mock/`: principal reference for consumer-authored custom lints (under `lints/`).

The comparison target is `/Users/orgrinrt/Dev/clause-dev/mockspace/`. Mockspace v2 layout: `mock/crates/mockspace-{cli,core,rs,template,config,test-fixtures}` plus workspace-root `bench-core`, `bench-macro`, `bench-harness`.

## Verdict by area

### 1. Bench harness: parity with one gap

v2 ships an equivalent bench-core + bench-macro crate pair at the workspace root. Same macro dispatch shape (`#[bench_variant(..., sizes = [...])]`), same cold/warm-cache discipline, same parameterised-N suite running. v2 added kuvio dep-graph visualization and integration with the render pipeline (#558).

**Gap**: v2 produces CSV but does NOT auto-generate the findings markdown that v1 polka-dots produced alongside (`coloring_n128_cold_findings.md`, `rcm_mega_run1_cold.md`, etc.). v1 had a CSV-to-findings.md pipeline that emitted one markdown file per (algo, n, cache) tuple, with summary stats and prose framing of the result.

`#590` was scoped to ship bench/sketch render slice 3 with this generator, but it was blocked on the `mock://` URI resolver, which is itself blocked on consumer demand. The bench-findings generator does not actually require the URI resolver; the resolver was a related but separable concern.

### 2. Sketch framework: partial parity

v1 sibling repos kept exploratory implementations under `research/` (loose convention, no formal subdirectory layout, sketches were just `.rs` or `.md` files dropped in alongside the SOURCES.md / SUMMARIES.md / *.pdf reference material). The v1 sketch was an executable artifact: code that ran, produced findings, then got absorbed into a design round.

v2 has a `mock/research/` directory but uses it for locked design memos (timestamped, lifecycle-tracked). The exploratory-sketch register lives implicitly in design round artifacts (topic.md, then doc CL, then src CL), and during round closure the sketch gets absorbed into the locked CLs and the original sketch is preserved as audit-trail.

This is asymmetric with v1 but not a functional gap: v2 design rounds carry more structure and the sketches the user might want are tracked under `mock/design_rounds/<timestamp>/`. The implicit convention works; making it explicit (a `mock/research/sketches/` subdirectory blessed by the template renderer) would add ceremony without adding capability.

**Action**: document the v2 sketch convention in the canonical workflow description so consumers know where to put exploratory work. No code change needed.

### 3. Custom lint surface: gap

v1 saalis ships custom lints (`no_vec_in_signatures.rs`, `register_on_impl.rs`) under `mock/lints/` and registers them via `Box<dyn Lint>` trait objects at the mockspace boundary. Consumer repos compose their own lint packs alongside the mockspace built-ins.

v2 mockspace ships 20 builtin lints under `mock/crates/mockspace-rs/src/builtins/` but has no consumer-extension surface. A consumer that wants to add a lint must either fork mockspace-rs (unacceptable) or wait for the viola plugin runtime (`#199`).

This is the audit's highest-impact gap. The clause-specific lint work tracked under `#11` is blocked on it. Three immediate-term resolution paths:

- **Path A** (correct, multi-day): unblock `#199` by shipping viola plugin scaffolding + porting the mockspace builtins as viola plugins, then exposing the plugin registration surface to consumers.
- **Path B** (interim): expose a `pub trait Lint` surface on mockspace-rs and accept `Box<dyn Lint>` from consumer crates at the engine boundary. Replicates the v1 saalis pattern; gets retired when viola arrives.
- **Path C** (deferral): document the gap, ship custom lints only inside mockspace itself for the rest of pre-1.0, push clause/arvo lint work to a later phase.

The pragmatic call: Path A is the correct long-term answer but Path B may be the right tonight-shippable interim. Decision deferred to a fresh design round; not implementable autonomously without trade-off framing.

### 4. Agent infrastructure: parity, restructured

v1 loimu used templated agent files (`MAIN.md.tmpl`, `PREAMBLE.md.tmpl`, `POSTAMBLE.md.tmpl`) plus `agent/{skills,hooks,rules,settings}/`. v2 replaces the template-engine surface with embedded markdown fragments under `mock/crates/mockspace-rs/src/agent_builtin/` (INDEX.md routes to identity / anchors / commands / suppressions / phases / sides / verbs). Bootstrap extracts the fragments via `install_agent_builtin()`. Same functional outcome, simpler implementation.

**Gap**: v1 had `agent/skills/` extensibility (consumer crates dropping their own skill files). v2 embeds skills as part of the builtin and does not expose a consumer-skill surface yet. This is the same architectural shape as the custom-lint gap: the builtin layer is comprehensive, but extension is awaiting viola.

### 5. Design round artifact rendering: parity

Byte-identical surface. v1 polka-dots has `mock/design_rounds/<timestamp>/{topic.<topic>.md, changelist.doc.lock.md, changelist.src.lock.md}` with `deprecated/` subdir for replaced CLs. v2 carries the same layout, lifecycle (plan, then doc CL, then src CL, then lock, then close, then archive), and lock semantics. The v2 render pipeline (#557 merged) produces equivalent artifacts.

### 6. Profiles, hooks, schemas, templates

Hooks: v2 PARITY ✓ (`#561` shipped pre-commit + pre-push; homma aggregation works).

Profiles: v2 GAP by design choice (`#568` removes preset infrastructure; replacement is per-repo `viola.toml` once `#200` lands).

Templates: v2 PARITY ✓ (mockspace-template crate handles every renderer the v1 siblings had, plus the render-fragment infrastructure from `#245`/`#246`).

`mockspace.toml` schema: v2 PARITY (v2 schema validated by `mockspace-config`; v1 schema was simpler but the v2 superset covers it).

## Process notes

This audit was produced by walking the three v1 reference repo trees and the v2 mockspace crate layout in one pass. Findings should be considered comprehensive for the bench / sketch / lint / agent / round / template surface but NOT comprehensive for edge-case behaviour (specific lint findings, specific bench results, specific template renderers). A finer audit would require running both v1 and v2 on the same inputs and diffing outputs.

The user's "first-class first-party" framing is what drives priority order: things v1 shipped well that v2 hasn't yet matched are the ones to focus on, not things v2 has reworked into a cleaner shape.
