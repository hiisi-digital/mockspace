# kuvio audit

Maturity + gap audit of `~/Dev/loisto/tools/kuvio`. Task #582. Feeds
the direction decision in #583 (adopt / finish / replace) for the
mockspace dep-graph rendering surface.

## TLDR

**Kuvio is further along than "hit a wall" suggested.** Build clean,
26 tests pass including a `full_pipeline_produces_valid_layout`
integration test, all 13 passes have substantive bodies with zero
TODOs / panics / unimplemented. The pipeline runs end-to-end on a
synthetic mockspace-shape graph (14 nodes, 22 edges) and produces
valid SVG.

**One concrete gap blocks merge quality**: the `SvgRenderer` does
not consume the `GroupEdgeRoutes` buffer that the
`GroupEdgeRouting` pass writes. Edges render as straight lines
between node centers instead of the orthogonal polylines the pass
computes. Single-function fix in `src/render/svg.rs`.

**Recommendation for #583**: **finish**. The work to reach adoption
quality is small (single renderer-side change), and the architecture
already matches workspace discipline (no `Box<dyn>`, atomic-ptr pass
dispatch, glam-based geometry, typed inter-pass buffers).

## Renderer gap (the actual wall)

`src/render/svg.rs:68-90` iterates `canvas.edges` and emits a `<line>`
between source-center and target-center for each. The renderer's
buffer parameter is `_buffers` (underscore prefix, unused).

Meanwhile `src/passes/group_edge_routing.rs:106-125` computes
orthogonal polyline routing through ports and writes a
`GroupEdgeRoutes` buffer. Read the file for the actual point
construction; the routing produces a vertical-only segment when
parent and source share an x-coordinate, otherwise a multi-point
orthogonal path through a horizontal midpoint segment.

The data is there; the renderer just doesn't consume it. Fixing
it is bounded: change `_buffers` to `buffers`, look up
`GroupEdgeRoutes` via `BufferStore::get::<GroupEdgeRoutes>`, join
each route back to its canvas edge, emit a `<polyline
points="..." fill="none" stroke="..." />` instead of the
straight `<line>`, fall back to the straight line when a route is
missing.

This is "finishing work", not "fundamental rewrite".

## Architectural fit with the workspace

- **No `Box<dyn>` dispatch**: pipeline.rs uses `AtomicPtr<u8>` with
  captured function pointers per pass. Matches the notko/arvo
  no-vtable discipline.
- **Typed inter-pass buffers**: `BufferStore` keyed by `TypeId`
  reads/writes. Pipeline validates buffer dependencies at
  `.build()` time. Matches the hilavitkutin scheduler-Resource
  shape philosophically.
- **Geometry**: `glam::Vec2` for coordinates, custom `Rect` for
  bounds. Reasonable; no novelty risk.
- **Metadata system**: `Value` enum (Str / Int / Float / Bool /
  List / Map) on Nodes. Drives grouping, sizing, coloring rules.
  Aligned with the workspace's "metadata drives layout" intent.
- **No alloc / no std**: kuvio uses `std::collections::BTreeMap`
  freely. This is a host-side dev tool, same exception scope as
  mockspace-rs. The workspace `no-alloc / no-std framing` rule
  explicitly carves out host-side tools.

## Other gaps for mockspace adoption (smaller)

1. **No README / STATUS / TODO in the crate root.** The "hit a
   wall" narrative the user mentioned isn't documented in the
   tree. Likely the user paused mid-rendering work (the
   GroupEdgeRoutes consumption above) and never wrote the wall
   down.

2. **No project_name / title rendering in SvgConfig.** The earlier
   `loimu/tools/mockspace/src/render.rs` Graphviz-side
   implementation had a title block (project name + subtitle). The
   kuvio SvgConfig lacks an equivalent field.

3. **No colors/style customisation plumbed through.** `SvgConfig`
   has `rules: Vec<StyleRule>` and `style.rs` defines
   `resolve_style`, but no example demonstrates the rule chain in
   action. Adoption would benefit from a concrete rule-by-metadata
   example.

4. **No golden-output snapshot tests.** Existing tests verify
   structural invariants (no-overlap, every-node-placed, every-
   edge-routed) but not the actual SVG body. Future renderer
   tweaks could regress visual output without test failure.

5. **No multi-graph examples committed.** The integration tests
   use `test_graph` (6 nodes). Real workloads will be larger.
   This audit's `render_sample.rs` example exercises the 14-node
   case successfully.

6. **Renderer trait `Renderer::render` discards buffers.** Even
   the trait signature has `_buffers` in the SvgRenderer impl,
   suggesting the renderer was scaffolded ahead of the layout
   passes producing usable buffers and never re-visited.

None of these are foundational; all are finishing work.

## Comparison vs alternatives (from #583's option list)

| Option | Fit for mockspace dep-graph | Effort |
|---|---|---|
| Keep Graphviz | Works today; user dissatisfied with aesthetic | Zero |
| Adopt kuvio as-is | Layout works; straight-line edges visibly cross nodes on 14+ node graphs | Low |
| **Finish kuvio** | Routed polylines + style rules + title would make it merge-quality | Modest (single-file + small additions) |
| layout-rs | Pure-Rust Sugiyama; less control than kuvio; unknown output quality | Low integration, unknown polish |
| D2 | Cleaner defaults but Rust integration weak; would require binary shell-out | Medium |

## Recommendation for #583

**Finish kuvio.** The investment is bounded (one renderer-side fix
plus three small additions: title block, style-rule example,
golden-snapshot tests), the architecture is sound, and the result
is full in-house control over dep-graph rendering with zero
external binary dependencies. Forgejo-migration-safe by default.

Suggested follow-up task chain after #583's decision:

1. Fix `SvgRenderer` to consume `GroupEdgeRoutes` polylines.
2. Add title block to `SvgConfig` (project_name, subtitle, font).
3. Add at least one `StyleRule` chain example demonstrating
   metadata-driven coloring.
4. Add golden-snapshot tests anchored to the audit's
   `render_sample.rs` outputs.
5. Add a README to the crate documenting the pipeline + the
   SvgRenderer API.
6. Wire kuvio into `mockspace_rs::render::dep_graph` as the new
   rendering path; keep the Graphviz `.dot` source emission as a
   second output (for users who want the source).

Estimated combined effort: roughly 1-2 firings of focused work
once the decision lands.
