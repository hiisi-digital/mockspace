## 1. The audit's findings, each answered

Every finding below was re-run by me with an independent script (`009_probes/p1_output.txt`, `p2_output.txt`, `p4_output.txt`), not taken from 007. The arms: U is a data worktree nested at a same-depth path no commit tracks, unhidden; H is the same hidden by the common `info/exclude`.

1. `clean -ffd` without `x`. Conceded. p1 section 1: arm U loses the edit to `clean -ffd` and `-ffdx` and keeps it to `-fd`, `-fdx`, `-ffdX`; arm H loses it to `-ffdX` and `-ffdx` and keeps it to `-ffd`. Neither of my files (002, 006) nor 001's listed it. The in-tree residual is therefore two double-force forms per arm, and they differ by arm.
2. A commit from another clone that tracks a regular file at the data path. Conceded, and it is the finding that hurts. p1 section 3, the polluting commit built by plumbing so no clone's hook could have stopped it: arm U, `checkout -f` and `reset --hard` onto it replace the edit with their bytes; arm H loses the edit to all four moves, including plain `checkout` and plain `merge`. My `006` section 4.2 rated pollution a "tidiness cost" after probing only the gitlink kind (`006_probes/p3`); that was a sampled law and I withdraw the sentence. A disjointness rule that each clone enforces by a hook is not a property any one clone controls.
3. The gitlink breaking `git submodule update`. Conceded. p1 section 4: with a 160000 entry at the data path and no `.gitmodules` mapping, `git submodule status` and `git submodule update --init` both exit 128 ("no submodule mapping found in .gitmodules for path"), for every clone of that branch. My `006` section 4.2 and `006_probes/p3` showed the data survives and stopped there, and the break of git's own submodule tooling is exactly what op's "git tooling unchanged" forbids. It is an argument against unhidden.
4. `pull` overwriting ignored files. Conceded. p1 section 5: `git pull --no-rebase` in the data worktree replaces an ignored local `output.txt` with the incoming tracked one; `git fetch` then `git merge --no-overwrite-ignore FETCH_HEAD` refuses ("untracked working tree files would be overwritten") and keeps the local bytes. `update` is therefore `fetch` plus `merge --no-overwrite-ignore`, never `pull`. The snapshot has to hold ignored files at paths the incoming commit tracks; the audit's a11 shows `ls-files -o -i --exclude-standard` with `add -f` does it. I did not re-run that part and take it from 007.
5. The shared branch name killing a mirror fetch in a bare clone. Conceded as a defect of the converged shape: I proposed the first data worktree on `mock/<ns>` and never ran a mirror-style fetch with it checked out. It disappears in section 2 below because no data ref is a local branch.
6. `git worktree lock`. Conceded as a good move for the cases it covers (`worktree remove` and `--force`, and `move`), taken from 007 a3 and not re-run by me. p1 section 2 adds what it does not cover: a locked data worktree is still removed by `git clean -ffdx` (the worktree list afterwards shows it `locked`, its files gone). A lock is a gate on `worktree`, not on `clean`.
7. The `core.fsmonitor` pre-write copy. Evaluated by probe, and it is the best idea in 007. `p4_output.txt`: a hook that records whether the edit is still on disk at the moment it is called was called, with the edit present, before `checkout -f`, `reset --hard`, `clean -ffdx`, `clean -ffd`, `stash -u`, `merge`, `cherry-pick`, `rebase`, `restore`, `switch`, `pull`, `checkout-index -f`, `read-tree -u --reset`, `am --abort`, `rm --cached`, `gc` and also `status` and `diff`. Not called for `worktree prune`, `bisect start`, `log`, `worktree remove --force`, `rm -rf`, and not called under `git -c core.fsmonitor=false clean -ffdx` (the edit was then gone with no hook call). So it is the only hook git runs before a destructive verb, it covers exactly the double-force cleans that the lock does not, and it is bypassed by one `-c`, by a person's own `core.fsmonitor` unless the engine chains to it, and by the verbs that never read the index. It also fires on `status` and `diff`, so it taxes every git command in the repository; I measured no cost and 007's 20 to 30 ms is an unbench. Verdict: adopt it as an optional best-effort layer whose entire claim is "bounds the loss to what the last call copied", never as the reason a verb is safe. Cost bench owed, in the harness.
8. The `git~1` path. p2 section (a): `git~1`, `GIT~1`, `.git.`, `.git ` (trailing space) and `.GIT` are refused by `git add -f`, by `update-index --cacheinfo`, and by `checkout -f` of a tree I crafted with `hash-object --literally`; `git~2`, `git~`, `gi~1` and an ordinary name are accepted. With `core.protectNTFS=false` the refusal is gone (`p2` section a2: `add -f` then tracks `git~1/x`). So it is git itself refusing every route a commit has to bring the path in, on a default configuration, which no hook of any clone achieves; that is the property op asked for ("much like git itself"). Limits, in order of weight: only one such name is usable at once for same-depth reasons (a second data directory would need a second name, and on a case-insensitive or NTFS filesystem `GIT~1` is `git~1` and the trailing dot and space forms are, I believe, the same entry as `.git`; an impression, not probed); it must be hidden, since unhidden it breaks `git add -A` of the whole tree (007 a10, not re-run); and a person can turn protection off. The name is op's call, as 007 says.

One audit claim was left unprobed by its author and I probed it. p2 section (b): with the data path in a tracked `.gitignore` on the code branch, a fresh clone that never ran the engine, an agent that writes research there and runs `git add -A` stages nothing; `git add <path>` refuses with git's ignored-path message; `git add -f` stages it. So the tracked `.gitignore` closes the accident and not the deliberate `-f`, and it closes nothing for a branch cut before the line existed (reading, not probed).

## 2. A ref layout that meets op's ruling

Requirements taken from op's words: a forge does not list data refs, a plain clone fetches none, only a clone that asks gets them, vanilla git keeps working where it can.

Layout probed in `009_probes/p3_output.txt` (a bare remote reached by `file://`):

- Remote: `refs/mock/<ns>`.
- Opted-in clone: a dedicated remote `mock-<ns>`, same URL by default, `fetch = +refs/mock/<ns>:refs/remotes/mock-<ns>/<ns>`, `tagOpt = --no-tags`, `push = HEAD:refs/mock/<ns>`.
- Local work ref: none under `refs/heads/`. Each data worktree's `HEAD` is a symbolic ref onto `refs/mock-wt/<ns>/<wt>`, made with `git worktree add --detach` followed by `git symbolic-ref HEAD`.

What the probe shows:

1. A plain `git clone`, `clone --bare` and `fetch --all` or `fetch origin` in a plain clone get no mock ref and not the data commit (`p3`, first block). `clone --mirror` gets it, which is a backup and right. In an opted-in clone `fetch origin` brings none and `fetch --all` brings it, so opting in is one remote and `fetch --all` follows it, as intended.
2. Inside the data worktree `git status` reads "On branch refs/mock-wt/research/main", `git commit` moves the ref, `git push mock-<ns>` (using the remote's push line) updates `refs/mock/<ns>`, and `git pull mock-<ns> refs/mock/<ns>` with explicit arguments merges a concurrent clone's commit and the ref follows. Bare `git pull` refuses ("You are not currently on a branch"), so `update` is an engine verb or a documented explicit command. With `core.logAllRefUpdates=always` the ref has a reflog and `ref@{1}` recovers a `reset --hard` (`p3`); under the default config the reflog of `refs/mock-wt/*` was not tested, only the always case.
3. `git push --all origin` from an opted-in clone leaks nothing: the remote's refs are unchanged (`p3`). The audit's leak came from a local branch `mock-wt/...` under `refs/heads/`; with the symref there is no such branch. That is the reason for the symref and not a branch.
4. `git push --mirror` is destructive in every layout and cannot be prevented from the client. From an opted-in clone with the remote-tracking mapping above, it deletes `refs/mock/<ns>` on the remote (the remote's refs after it do not list it) and also publishes `refs/mock-wt/*` and `refs/remotes/*` (`p3`, "after push --mirror (opted-in)"). From a plain clone it deletes it (the plain-clone block). With an identity mapping (`fetch = +refs/mock/<ns>:refs/mock/<ns>`) an up-to-date opted-in clone's mirror push keeps the ref, and a stale one rewinds it: `p3` last line, the newer data commit "is no longer reachable from the remote ref". The extra refs it publishes are not under `refs/heads`, and a new plain clone after the opted-in mirror push has only `refs/heads/dev` and its remote-tracking refs (`p3`, plain2). Whether a forge shows `refs/remotes/*` is not probed. `--mirror` means "make the remote equal me" for every branch of the repository, so this is the same class as deleting everyone's branches, not a new hole; but for data it is a loss on the remote, recoverable only from an opted-in clone's tracking ref. I choose the remote-tracking mapping (`refs/remotes/mock-<ns>/<ns>`, git's own convention): a delete is visible on the next fetch and the tracking ref still has the tip, where an identity mapping can silently rewind. That is taste with this measured difference, labelled as taste.
5. The remote URL of the dedicated remote can be another repository. `p5_output.txt`: with `mock-research` pointing at a second bare repository, two clones exchanged data through it, `git pull` in the data worktree ran the main repository's custom merge driver (`a b x y`), `origin` held only `refs/heads/dev` and the data repository only its data branch. The data worktree is a worktree of the main repository's object store either way; only where objects travel changes. This answers 001's reason for rejecting a second repository (config does not follow into it): it does follow, because the repository is not a second one, only its remote is. (p5 printed one `fatal: HEAD not found below refs/heads!` line from a `git branch -D` step of the script that I did not chase; the merge and the ref contents it reports are what the run produced.)

Not probed and stated as unprobed: refusal or acceptance of `refs/mock/*` by a real host. `mock/crates/mockspace-store/src/refs.rs:16-19` records a proxy that accepted `refs/heads/mock/probe` and hung up on `refs/mock/probe` and `refs/notes/mock-probe`. I tested no forge and no proxy; a push of probe data to a real account is not something I do without being asked. If the hosts op uses behave like that proxy, point 5 is the vehicle: the dedicated remote names a second repository on the same host, whose own `refs/heads/` is its business and which no one clones by accident. That fallback is a config line away from the primary layout, so the layout does not have to be decided by the host check; the URL does.

## 3. The revised build, whole

What stays from the converged shape: one branch form deleted in favour of the layout above (so `RemoteForm::Branch` and the local `refs/mock/<ns>` mirror of the shipped engine go, `mock/crates/mockspace-store/src/refs.rs:46-62`); the data is a native worktree of the main repository; the engine's index, ignore, filter, sparse, hook and merge reimplementations go (`instance/*`, `src/data_refs/sparse.rs`, `hook.rs`); the snapshot is built through a git index and held by a ref; merge drivers, LFS (`004_probes/p3`) and hooks are git's; `Mock-Ref` pairing stays; templates move into the data tree if op accepts (open fork).

1. Remote and refs. As section 2. Namespace rule at declaration: refuse a namespace that is a path prefix of another (`004_probes/p2` D/F collision), keep `refs/mock-backup/<ns>` untouched, and name the cache `refs/mock-cache/<ns>/<wt>`, one ref per data worktree with history carried by parents.
2. Placement. In the tree, same depth as the path replaced, on a path no history tracks, physical so the 13 of 24 research manifests with `../../..` keep working (`006_probes/p1`).
3. Pollution, class by class, because p1 section 3 shows it is the dominant loss and no single mechanism closes it.
   a. Where op accepts the untrackable name, the one data directory that needs same-depth relative paths takes `git~1` and no commit from any clone can write it (p2a). Hidden by the common `info/exclude`.
   b. Every other data directory: hidden by a tracked `.gitignore` line on the code branch, committed by the migration (p2b); plus a detective, not preventive, check in `verify`, in the pre-push hook and in a CI lint that no commit tracks any file or gitlink at a declared data path. This does not prevent a polluting commit from a branch cut before the line existed, or a `git add -f`; p1 section 3 shows what that costs the next person who moves the main tree onto it. I do not claim it is closed. It is bounded by item 5.
4. Verbs, each a git command run in the data worktree: `instantiate` (create the dedicated remote and refs, `worktree add --detach`, set the symref, lock the data worktree and the linked parent worktree with a reason); `status` (git's, per data worktree, printing the data path as data); `update` (`fetch` then `merge --no-overwrite-ignore`, snapshot first); `commit` (repo lints, then a real `git commit` in the data worktree so hooks, signing and filters apply, which also fixes the `--no-filters` path the audit confirmed at `instance/files.rs:228`); `push` (explicit refspec from the remote's push line); `verify` (worktree exists and is locked, HEAD symref is the declared ref, no ref of the data under `refs/heads/`, exclude and `.gitignore` lines present, no tracked file at a data path, no `core.protectNTFS=false` when the untrackable name is used, namespace nesting).
5. Recovery cache, three layers, none relied on. (i) The ref-held snapshot before every engine verb that writes: a temporary index started as a copy of the data worktree's own index (the copy costs about a twelfth of a fresh index at 3000 files, `006_probes/p2`), plus ignored files at paths the incoming commit tracks. (ii) The one-day user cache directory, the only layer that survives deleting the clone. (iii) The optional fsmonitor layer of section 1 item 7, which copies before the double-force cleans and the checkout, reset and stash verbs and is documented as bypassable.
6. Locks. `git worktree lock` on every data worktree and on the linked worktree that holds it. It covers remove, `--force` and `move`; it does not cover `clean -ff*` (p1 section 2), which is why item 5 exists.
7. Residual loss, stated exactly. With a person who types `git clean -ffd[x]` or `-ffdX` in the main worktree, or `rm -rf`, uncommitted data edits made since the last snapshot or fsmonitor copy are lost, and committed data survives in the branch ref and the remote. A polluting commit from a branch the item 3b checks missed overwrites an unrelated edit when someone moves onto it (p1 section 3, arm H worst). `push --mirror` from any clone deletes or rewinds the remote data ref (section 2 point 4), recoverable from any opted-in clone. None of these is zero and I will not write a sentence that says so.
8. Migration, from v1 and from the shipped v2. Owed in full and not designed here. Constraints I can state: snapshot to the ref and the user cache before any step; keep `refs/mock-backup/<ns>` and fold the pending commit files into refs first (`pending.rs:17-20`); the shipped local `refs/mock/<ns>` mirror and the remote `refs/heads/mock/<ns>` are moved by an explicit push to `refs/mock/<ns>` and only then deleted; each step idempotent and verified byte for byte before an original is removed.
9. Tests owed as contracts. The verb rows of p1 (all clean forms, polluting commit by plumbing, gitlink and submodule verbs, pull over ignored) crossed with the arms and the clone shapes (normal, linked, bare with linked); the remote rows of p3 (plain clone, bare, `fetch --all`, `push --all`, `push --mirror` from plain and opted-in, stale mirror); p4's coverage table as a test of the fsmonitor layer including its documented bypasses; the red bare-clone test (it must go green by the absence of any `core.bare` edit).
