## 2. Where 001 is wrong, unsupported, or weaker than the alternative

### 2.1 Its chosen shape leaves a documented loss path that mine removes

001 section 3 places the data worktree inside the main work tree at a path no commit has tracked, hidden by `info/exclude`. 001's own p6 shows what removes it: `git clean -ffdx` ("Removing mock/", `001_probes/p6_output.txt`), and the section 3 closing paragraph lists it: "Edits in a data worktree vanish with `git clean -ffdx` (two f)". My `002_probes/p2_output.txt` last block measured the same thing, and `002_probes/p4_output.txt` shows the alternative: the worktree under the common git directory with a symlink in the tree. `clean -ffdx` removes the link and the edit stays in the real directory. So inside-the-tree is a strictly larger loss surface than outside-the-tree for the same data, by a command a person types without thinking of it as a hard reset.

Replacement. Keep 001's central point (a path no old commit tracked) and put the worktree outside the main work tree, under the common git directory. What it costs is exactly what 001 was avoiding: the main tree needs a way to reach the data. Two ways, and they are separable: the engine's resolver names the real path (the path move 001 already accepts), and a directory symlink at the legacy `mock/<dir>` is an optional convenience for tools that read the legacy path. The symlink never carries data, so the relink step is the only extra mechanism: if the link's place holds a real directory (old commit wrote there, `002_probes/p4_output.txt` sixth row), rename it aside, never delete. 001 has no such step because its path never collided; that is a point for 001's path choice, and I take it: the canonical path should be the disjoint one, with the link as the legacy view, not the other way round as my `002` 3.1 item 3 had it. Without the symlink, 001's resolver change stands and the data is safe from `clean -ffdx`. Whether to keep the legacy link at all is op's call (no-legacy-shims pre-1.0 argues against it); I do not decide it.

### 2.2 Reading B, the replace-ref view, has a hole 001 did not probe, and I did

001 p7 shows `git replace OLD REP` keeps an edit alive across `checkout -f OLD` and `reset --hard OLD` ("edit survives: 1" twice). I accept that result for the commit that was replaced. 001 section 3 item 4 B states the costs it saw (fresh clone has zero replace refs, hosting limit, regeneration after fetch). It missed the larger one: a replace covers only commits that exist when it is made. A branch cut before the migration continues to receive new commits in the old shape, which track the data path again.

`004_probes/p1_output.txt`: with OLD replaced, the forced trip over OLD kept the edit (`edit = EDIT`, reproducing p7). Then a new commit on the branch cut at OLD, in the old shape (`new tip tracks: c.rs mock/research/M.md mock/research/N.md`), and an edit on dev, then `checkout -f` of that new tip: the edit is replaced by the branch's bytes (`edit = feat-edit`, where `EDIT2` would mean kept). The window 001 names ("a window between fetch and regeneration") is not a window; it is every commit made on an unmigrated branch, forever, until someone regenerates after each one. Reading B should be struck, not carried as "plausible, fragile": it cannot close the forced way back, only close it for history that already existed. That also answers 001's own stated wall ("I found no way to make `checkout -f OLD` safe at the old path without either the replace-ref view or moving the path"): the replace view is not a second way, so the wall is single-sided, and only a path nobody tracks gets through.

### 2.3 A defect in 001's snapshot naming, found by probe

001 section 3 item 6 names the snapshot `refs/mock-backup/<ns>/<worktree-name>`. The shipped engine already keeps `refs/mock-backup/<ns>` (`mock/crates/mockspace-store/src/instance/backup.rs:6`). `004_probes/p2_output.txt`: with the shipped name present, `update-ref refs/mock-backup/research/wt1` fails (`'refs/mock-backup/research' exists; cannot create ...`, rc 128), and the reverse also fails. A migration of the engine's own backups to 001's layout cannot be made in place; each existing ref must be read, moved aside and deleted first, or the new layout must be a different prefix. The same D/F collision applies to my `002` 3.2 item 7 name `refs/mock-cache/<ns>/<n>` when two namespaces nest (`refs/mock/a` against `refs/mock/a/b`, same output), so the proposal must say how namespaces nest. Probe: whether `validate_namespace` admits a namespace that is a path prefix of another; I did not run that check against the store's validator. Replacement: give the cache a leaf name that cannot be a directory, one ref per (namespace, worktree) with history carried by parent commits, and make the engine refuse namespaces that are a prefix of another before any ref is made.

### 2.4 One data branch per main worktree: an unmeasured cost

001 section 3 item 2 gives each linked worktree its own local branch (`mock-wt/<ns>/<worktree-name>`) tracking the shared one, so data edited in two sibling worktrees of one clone is two copies that must be merged with each other by `git pull` through the remote or a local fetch. The brief calls the directory shared. My shape (one worktree per clone, every main-tree worktree reaches it) removes that: there is one copy, git's index lock in it serialises, `002_probes/p5_output.txt` shows both linked worktrees of a bare clone reading the same bytes. What mine costs: every worktree sees the same data whatever branch of the code it has checked out. That is a semantic question about the directory ("is research per branch of code?") that neither file settles, and it is op's. Which of the two is right is therefore not a probe question; but 001's choice is stated as "git's rule" (one branch, one worktree) when git's rule only forces a distinct branch if there are several worktrees, and 001 did not run its own variant (001 section 5 item 9: "was not run"). A proposal whose bare-clone case is unrun is an impression on the case op's second red test is about.

## 3. What should stand, combined
