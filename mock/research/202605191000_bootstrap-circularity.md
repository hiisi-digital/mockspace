# Bootstrap circularity: design for mockspace dogfooding itself

## The shape of the problem

mockspace v2 is being implemented inside the mockspace repo itself. Two systems compete for the same repo state while v2 lands:

1. **v1 mockspace's bootstrap.** `cargo mock` on a v1-shaped consumer repo writes `.cargo/config.toml` (with the `cargo mock` alias), generates per-repo git hooks under `mock/target/hooks/`, and points `git config core.hooksPath` at them. The bootstrap self-activates on first `cargo check` inside `mock/`.

2. **The workspace homma gate** (`~/Dev/clause-dev/.claude/hooks/_workspace--mockspace-gate.sh`, generated by `homma agent regen` per task #473). On every `git commit` / `git push` Bash tool call, it inspects the active member repo's mockspace surfaces and either silently allows (0-of-3 or 3-of-3 adoption signals) or denies with a `homma agent regen --repo <name>` prompt (partial 1-of-3 or 2-of-3).

The three adoption signals the gate checks:

- `<repo>/mock/` directory exists.
- `<repo>/.cargo/config.toml` carries a `^mock\s*=` entry (the `cargo mock` alias).
- `git config core.hooksPath` returns non-empty inside the repo.

mockspace ships `mock/` and `.cargo/config.toml` with the alias, so signals 1 and 2 are present. Signal 3 is intentionally absent during v2 development: running v1's stale hooks against v2 design rounds would either no-op meaningfully (the locking machinery the hooks invoke is exactly what v2 redesigns) or fail in confused ways against the in-flight v2 schema (the spec adds new ref shapes the v1 hooks don't recognise).

The gate's 2-of-3 case kicks in, denies the commit, and prompts a regen, which would either re-run v1's bootstrap (re-activating the hooks we want disabled) or fail when the alias resolves to a binary that doesn't yet handle the in-flight ref shape.

That's the surface symptom. The deeper question is: how does mockspace v2 cleanly dogfood itself once it ships? The workaround documented at the end of this note is the immediate bridge; the design proposal in the middle is the load-bearing answer.

## Design: one mechanism for everyone, `mock_bin_path` resolves it

There is no flag that says "the mockspace repo is special". There is one config field, `[mockspace] mock_bin_path`, that anyone can set, with a sensible default-discovery order. The mockspace repo happens to be the one place that always sets it; downstream consumers usually leave it unset.

### One invocation API: `mockspace_call()` + `resolve_invocation()`

Hook generation is one consumer of "how do I invoke the mock binary". There are others: `mock doctor` spawning `mock refresh`; future internal sub-command dispatch; third-party Rust callers that need to drive mock programmatically. All of them go through one shared pair in `mockspace-rs`:

```rust
pub enum ResolvedInvocation {
    Absolute(PathBuf),   // steps 1, 2, 3
    CargoAlias,          // step 4
}

pub fn resolve_invocation() -> Result<ResolvedInvocation, ResolutionError>;

pub fn mockspace_call<I, S>(args: I) -> Result<ExitStatus, CallError>
where I: IntoIterator<Item = S>, S: AsRef<OsStr>;
```

`mockspace_call(["doctor"])` spawns `mock doctor` using whatever the resolver returned. `bootstrap::install()` calls `resolve_invocation()` at hook-write time to bake the result into the proxy scripts. Internal sub-process spawns call `mockspace_call()` at invocation time. Every code path that touches "which binary do I invoke" goes through these two functions; any change to the priority chain, new resolution steps, or spawn-time semantics lands here once and propagates everywhere.

### Resolution order

`resolve_invocation()` runs this chain (5 steps, highest precedence first):

1. **`MOCKSPACE_BIN_PATH` env var** if set and points at an executable. Highest precedence so the bootstrap's own choice propagates: bootstrap-generated proxies set `MOCKSPACE_BIN_PATH=<resolved>` on the exec line, so the running mock binary's own resolution (for any sub-process it spawns) sees the same value. No drift between proxy generation and binary execution.

2. **`[mockspace] mock_bin_path` in `mockspace.toml`** if set. The explicit-config case for the persistent setting (the env var is volatile per-process; the toml field survives across invocations).

3. **`which mock` on `$PATH`**. The cargo-install / homebrew / package-manager case.

4. **`cargo mock` probe**: try `cargo mock --version`; on success, the hook is generated as `exec cargo mock hook <event>` (cargo handles binary lookup at invocation time). Belt-and-suspenders for environments where the binary exists but isn't directly on PATH (cargo bin shim, alias-resolved location).

5. **Error**: refuse to write hooks; `mock doctor` reports the failure and surfaces remediation (`cargo install mockspace`, set `MOCKSPACE_BIN_PATH`, set `[mockspace] mock_bin_path`).

`mockspace.toml` shape:

```toml
[mockspace]
# Optional. Falls through the resolution order above when unset.
# Path is relative to this mockspace.toml's directory; absolute paths
# warn at config-load (the value still resolves, the warning surfaces
# via the structured diagnostic sink). Examples:
mock_bin_path = "target/release/mock"   # mockspace's own dogfood case
# mock_bin_path = "../../bin/mock"      # monorepo with mock elsewhere
```

mockspace's own repo sets the toml path to its locally-built binary. Downstream consumers leave the field unset and rely on step 3 (or step 4 as fallback). Anyone can override at any step for any reason: alternate install location, vendored binary, sandbox, build-mode toggle.

### Portable paths: relative anchored at the containing config

`mock_bin_path` must work across clones and machines. The anchor for resolution is the directory containing the `mockspace.toml` that declared the value. Absolute paths (Unix-style leading `/`, Windows drive-letter prefixes) work but trigger a structured warning at load time, because the most common reason for an absolute path showing up in a portable field is "I pasted my local laptop's path" rather than a considered choice.

The warning generation is a shared helper that any path-shaped config field with the `portable: true` schema-marker uses. The helper is the single point of maintenance for the relative-path policy; future refinements (stricter form, fix-patch suggestions, lint integration, additional probe heuristics) live in the helper, not scattered per field.

Marking is per-field at the schema layer. `mock_bin_path` is `portable: true`. External-tool paths (system binaries living outside any repo) stay `portable: false` and the helper is bypassed for them.

Generated hook script (steps 1-3 emit the absolute-path form; step 4 emits the cargo-alias form):

```sh
# Absolute-path form (steps 1, 2, 3)
MOCKSPACE_BIN_PATH="/abs/path" exec "/abs/path" hook pre-commit "$@"

# Cargo-alias form (step 4)
exec cargo mock hook pre-commit "$@"
```

The absolute-path form bakes `MOCKSPACE_BIN_PATH` as an env-var on the exec line. Sub-processes the mock binary spawns inherit it; their own resolution chain finds step 1 satisfied without re-running discovery. The cargo-alias form does not bake the env-var (the alias's own resolution already produced the working invocation; sub-processes go through the chain again themselves, in practice hitting step 4).

The `cargo mock` alias in `.cargo/config.toml` continues to work for interactive use, independently of how hooks are wired.

### Why this is one mechanism, not two

The earlier shape proposed a boolean `self_hosted` flag that switched hook generation between two branches. That framing is wrong: there is no inherent "self-hosted vs consumer" dichotomy, only a binary-resolution question. Once the question is "where is the binary?", the answer is a path, not a flag. A path field has these properties the flag lacked:

- **No misleading name.** "self_hosted" sounds like a deployment mode (Saas vs on-prem; integrated git vs standalone). The actual question is "which binary do I exec from this hook".
- **No special-case branch in code.** The bootstrap reads one field, runs a resolution chain, writes the path. The mockspace repo and a consumer repo run the same code path.
- **No silent gotchas.** A flag-shaped invariant ("self_hosted is true exactly when this is the mockspace repo") is enforced by discipline; a path-shaped field describes reality directly. If `mock_bin_path` resolves to a working binary, hooks fire. If it doesn't, doctor refuses.
- **It composes.** Future scenarios (e.g., a workspace with a vendored mock binary in a sibling directory) work without further config additions.

### Activation: one unconditional call, all gating internal

The build.rs sketch becomes a single unconditional call:

```rust
fn main() {
    mockspace_rs::bootstrap::install()
        .expect("mockspace bootstrap failed");
}
```

`bootstrap::install()` owns all activation logic internally. It reads `USE_MOCKSPACE=1` from the environment as the opt-in switch: when unset (the default), `install()` returns Ok without writing anything. When set, it runs the resolution chain, writes hook proxies, writes the `cargo mock` cargo alias, and updates `core.hooksPath`.

Pushing the gate inside the function has two payoffs:

1. **The consumer's build.rs has no conditionals.** One line, always the same shape, no chance of consumers diverging on how they call us.
2. **Future activation conditions land inside `install()` without touching any consumer.** If we later add a "skip when running under `cargo publish`" guard, or "skip on CI without an explicit override", consumers don't update their build.rs.

The function name reads as "install mockspace's integration into this repo", parallel to `cargo install`, `husky install`, and similar tooling-integration verbs. Companions live alongside in the same module: `bootstrap::refresh()` re-runs resolution and rewrites stale proxies (called by `mock doctor`); `bootstrap::uninstall()` removes the integration; `bootstrap::status()` reports current state.

During v2 development on the mockspace repo, `USE_MOCKSPACE` stays unset. `install()` no-ops. The transition bridge (the empty hooks directory workaround) keeps the workspace gate happy while install is dormant. Once the v2 binary handles the current ref shape and surfaces an acceptable agent UX, set `USE_MOCKSPACE=1` and re-run `cargo check`. `install()` activates, resolves the binary path via the 5-step chain, and writes hooks. The empty-dir workaround retires (`rmdir .git/v2-dev-no-hooks`).

`homma agent regen --repo <name>` sets `USE_MOCKSPACE=1` explicitly when running per-repo regen. The v1 invariant survives v2.

### Crate placement: bootstrap lib lives in `mockspace-rs`

The bootstrap function is Rust-specific (it writes a `cargo mock` alias and depends on `cargo` semantics). It belongs in `mockspace-rs` per spec §57, not in the language-agnostic `mockspace` core or `mockspace-config` / `mockspace-template` libs.

For the build-dep relationship from mockspace's own `mock/`:

```toml
# mockspace/mock/Cargo.toml (or wherever mock/'s build-dep lives)
[build-dependencies]
mockspace-rs = { path = "../crates/mockspace-rs" }
```

The lib crate exposes `bootstrap::install()` as the public entry. Consumer repos declare a git build-dep instead:

```toml
# downstream-consumer/mock/Cargo.toml
[build-dependencies]
mockspace-rs = { git = "https://codeberg.org/orgrinrt/mockspace.git", rev = "<sha>" }
```

Both call the same function. `install()` checks `USE_MOCKSPACE`, runs the resolution chain, writes proxies, and returns. There is no branching code path for "am I in mockspace?". The mechanism is uniform.

### Why not git-ref versioning?

A version-isolated bootstrap (mockspace depends on a prior published version of itself via git ref to generate hooks) would solve a problem we don't have: there is no version-coordination question, because the bootstrap is reading config and resolving a path, not generating code that depends on its own future shape. Path-dep through the same Cargo workspace gives the lib-first build ordering that git-ref would also provide, without the version-coordination overhead. Downstream consumers still use git-ref (their build-dep points at a specific mockspace commit); the mockspace repo uses path-dep on its own member crate.

## Transition bridge (current workaround)

Until the self-aware bootstrap lands, the empty hooks directory keeps the workspace gate happy:

```bash
# In ~/Dev/clause-dev/mockspace
mkdir -p .git/v2-dev-no-hooks
git config core.hooksPath .git/v2-dev-no-hooks
```

The directory exists but is empty. git's hook lookup walks it, finds nothing matching `pre-commit` / `pre-push`, and runs the commit unchecked. The workspace gate sees `core.hooksPath` set, counts 3-of-3 adoption signals, and silently allows. No v1 hook fires. v2 implementation work proceeds with no interference.

The bridge is reversible by removing the empty dir and unsetting `core.hooksPath`. It mutates nothing else in the repo.

## Failure modes the workaround does NOT cover

- **An agent or user runs `cargo mock`** inside the mockspace repo. The alias still resolves (signal 2 is intact) but the binary it dispatches to is v1, which assumes v1-shaped round files. Outcome: confused errors from a stale binary trying to parse a forward-incompatible schema. Mitigation: don't run `cargo mock` in this repo until v2 ships; rely on direct git workflow during Phase 0 implementation.

- **A future `homma agent regen --repo mockspace` invocation** would notice the empty hooks directory (`core.hooksPath` is set, so 3-of-3, no drift flagged) and proceed as if the repo were fully adopted. If the regen step writes v1 hooks back into `mock/target/hooks/` and re-points `core.hooksPath` at that location, the workaround is undone. Mitigation: avoid running homma's agent regen for the mockspace repo specifically until v2 ships. The other nine workspace repos can run regen freely.

- **Stale `.cargo/config.toml` alias contents.** The alias body in `.cargo/config.toml` still points at v1's binary signature. The alias body will be rewritten when v2's `mockspace-rs` ships its own bootstrap. No mitigation beyond user awareness for now.

## Retirement: self-hosting goes live

The full sequence retires the workaround in five steps. Each step has a corresponding task; the chain is named here so a future agent picking up the work sees the order:

### Step 1: Phase 5 (`mockspace-rs` lands)

Per the v2 phase plan, Phase 5 (#484) covers hooks + profiles + CLI, which is where `mockspace-rs::bootstrap` lives. The self-aware bootstrap function ships as part of Phase 5. A dedicated sub-task (created from this note) tracks the self-hosting logic specifically.

### Step 2: Path-dep mockspace's own `mock/` workspace on `mockspace-rs`

Add the `[build-dependencies] mockspace-rs = { path = "..." }` line to mockspace's own `mock/Cargo.toml` (or wherever its build-dep root lives). The build graph now compiles `mockspace-rs` before invoking the mock workspace's build.rs.

### Step 3: Enable self-hosting explicitly

Set `[mockspace] self_hosted = true` in `mockspace/mock/mockspace.toml` (the new v2 schema; see §46). The bootstrap reads this flag and routes hooks at the local binary path rather than the alias.

### Step 4: Activate

```bash
USE_MOCKSPACE=1 cargo check  # in mockspace/mock/
```

The build.rs bootstrap fires, generates v2 hooks, points `core.hooksPath` at them. The empty `.git/v2-dev-no-hooks` directory becomes unused.

### Step 5: Verify and clean up

`mock doctor` confirms the hooks are functional. The empty dir can be removed (`rmdir .git/v2-dev-no-hooks`) once `core.hooksPath` is re-pointed. A short integration test confirms that running `cargo mock <subcommand>` inside mockspace's own repo behaves identically to running it inside a downstream consumer.

If divergence appears, the divergence is itself a v2 bug to fix. The dogfooding is the test.
