# The review of the repository running its own gates

Fixes from the review of rounds `202611240329` and `202611240338`.

## Where the config schema is strict

`mockspace-config`'s design said every key the file does not have is a parse error. Only the root, the inline form of an import, a preset file and its severities carry `deny_unknown_fields`; `[mockspace]`, `[refs]`, `[hosts.<name>]` and the other sections do not, so `[mockspace] verison = "2.0"` parses and the key is dropped.

Options weighed:

- Make every section strict. It is what the crate's own comments argue for the import and preset forms (a typo otherwise resolves silently and loses the author's intent), and what the v1 engine does with its config.
- Narrow the design to what the code does.

Spec §46 says neither, and this repository declares no canon, so the design stands in for one and its silence is not settled here. Settled: the design and the readme say exactly where the schema is strict, a test pins both sides, and whether the sections should refuse an unknown key is a question put to the maintainer. The test that pins the sections is the one that changes when it is answered.

## The builtin-lints lock

The root test read only `[dependencies]` and `[build-dependencies]`; a branch dependency under `[dev-dependencies]`, `[target.<cfg>.*]` or `[workspace.dependencies]` escaped it. It reads every dependency table now. That the lock holds the commits viola's own lock holds is checked by nothing, since viola is not in this repository, and the manifest says so.

## Names that do not belong in published text

`mockspace-template`'s documents, rendered into `docs/TEMPLATE.md`, named a tool of the maintainer's estate and used a word the project's prose avoids; `mockspace-config`'s backlog used the same word, and `mockspace-rs`'s backlog named the estate and a path in it. Each is reworded to say what it means.
