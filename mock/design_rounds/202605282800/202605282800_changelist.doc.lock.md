# Doc changelist: bucket-3 no-duplicate-fn cdylib evaluator (two-phase)

**Date:** 2026-05-28
**Phase:** DOC (locked)
**Round:** 202605282800

The cdylib carries no `DESIGN.md.tmpl` in the tool doc tree, so this round's design narrative lives in the CLs themselves (mirroring the prior cdylib rounds 202605282500/282600). This doc CL records the design decisions; the src CL records the mechanical source changes.

## D1: two-phase vtable binding

This is the first project-scoped cdylib lint. It binds `LintEvaluateProjectIndexVtable` (from viola-plugin-abi #618) rather than the per-file `LintEvaluateVtable` the eight existing providers use. The provider's `VTABLE_PTR` addresses a `LintEvaluateProjectIndexVtable` static carrying two fn pointers: `index_phase` and `evaluate_phase`.

## D2: provider id is the canonical project id

The ABI ships ONE canonical project provider id (`PROVIDER_LINT_EVALUATE_PROJECT = "viola.lint.evaluate-project.v1"`). A descriptor carries one provider entry per project lint, each pointing at its own two-phase vtable; the host distinguishes a project lint from a per-file lint by which vtable shape the entry carries, not by a per-lint id. The lint's identity (`no-duplicate-fn`) travels in the emitted diagnostic's `rule_id`, exactly as the per-file lints carry their identity in `rule_id` while sharing the per-file vtable shape. `PROVIDER_NO_DUPLICATE_FN` is therefore an alias of `PROVIDER_LINT_EVALUATE_PROJECT`, named for readability at the provider-export site.

## D3: full-project nam in both phases

The `LintEvaluateProjectIndexVtable` doc comment states the host calls `index_phase` once with the full NAM, then `evaluate_phase` per file. `evaluate_phase` carries both `nam` and `file_idx`. The `file_idx` selects the file to evaluate within the full-project `nam`; a per-file `nam` would make `file_idx` redundant. The evaluator reads `nam` as the full-project payload in both phases: `index_phase` walks every entry; `evaluate_phase` evaluates `entries[file_idx]` and cross-references the project-wide index for the rest.

## D4: file-vs-crate approximation

The in-process rule groups by crate (a duplicate must span at least two crates). NAM gives the cdylib per-file granularity, not crate identity, so "crate" maps onto "file": a cross-FILE duplicate is the flagged shape. Faithful for the common one-fn-per-file-pair case; a future schema carrying crate identity per entry would restore exact crate grouping. Documented at `index_phase`.

## D5: name-hash grouping with byte confirmation

`index_phase` stores per public top-level function a locator (`file_idx`, `node_idx`), an FNV-1a `name_hash`, and an FNV-1a `sig_hash` over the parameter type-leaf spans. `evaluate_phase` groups by `name_hash` (the in-process rule's primary by-name path) and confirms every hash match by re-reading the other record's name from its NAM source span and comparing bytes. A hash collision can only cost a redundant byte comparison, never raise a false positive. The signature hash is carried for parity with the in-process rule's signature axis and as a cheap tie-breaker; the firing path is name-based, so the param-only signature hash (return-type position has no v1.3.0 node kind) does not change which duplicates fire.

## D6: top-level + public scoping

Indexed functions are direct children of a file's SOURCE_FILE root (the rule `item_metric` already uses for top-level items) that are FUNCTION_ITEM and pass the exact-`pub` visibility check `node_is_public` applies. A nested fn under a mod or impl is not a top-level item and is not indexed, matching the in-process rule walking only the crate root's direct `function_item` children. A same-file duplicate does not fire (the cross-file check requires a different `file_idx`); the rule flags cross-file reuse opportunities, not same-file overloads.

## D7: undocumented-type deferred

The other bucket-3 lint, `undocumented-type`, is not in this slice. Deciding whether a public item carries a doc comment needs the doc-comment text adjacent to each item plus an attachment inference (which comment attaches to which following item). The v1.3.0 NAM node array carries LINE_COMMENT / BLOCK_COMMENT kinds but no doc-attachment edge, and re-deriving attachment from comment-node adjacency is a separate design question. Deferred to its own round.

## D8: caveat (synthetic-test-only until producer + host loop land)

No real NAM producer exists (the rust-native runner is #220, blocked by #195/#471), and the two-phase host dispatch loop is deferred (#618 shipped only the ABI surface). This evaluator is unit-tested against synthetic multi-file `NamNode` arrays and hand-allocated `IndexBatch` buffers; end-to-end validation arrives when both the producer and the host loop land. The port readies the lint ahead of both, matching the schema-ahead-of-producer posture of the per-file ports.
