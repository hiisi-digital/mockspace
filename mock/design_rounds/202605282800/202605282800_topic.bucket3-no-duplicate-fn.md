# Why this round exists

The in-process `no-duplicate-fn` builtin (`mockspace-lint-rules/src/no_duplicate_fn.rs`) is a cross-crate lint: it collects every public function across crates, groups by name, and flags a function whose name also appears in another crate (the by-name path) as a reuse opportunity. It is the canonical bucket-3 lint, the one that motivated the two-phase project-scope ABI shape: a per-file evaluator cannot see other files, so a cross-file duplicate needs a project-wide index built before any per-file evaluation runs.

Porting it onto the two-phase boundary exercises `LintEvaluateProjectIndexVtable` end-to-end (index_phase building the project index, evaluate_phase reading it back per file) for the first time, and gives the host a project-scoped lint to dispatch once the two-phase host loop lands.

# What lands

A two-phase evaluator behind `PROVIDER_NO_DUPLICATE_FN` (the canonical `viola.lint.evaluate-project.v1` provider id), registered in the `#[export_extension]` providers list as the ninth provider. Its `index_phase` walks every file's NAM node array and writes one `IndexRecord` per public top-level function into the host-owned `IndexBatch`; its `evaluate_phase` reads the index back for one file and emits a diagnostic per public function whose name has a confirmed cross-file twin. Plus an `IndexRecord` `#[repr(C)]` carrier, name + signature hashing helpers, and eight unit tests against synthetic multi-file `NamNode` arrays with hand-allocated `IndexBatch` buffers.

# File-vs-crate approximation

The in-process rule groups by crate: a duplicate must span at least two crates. NAM's per-file granularity gives the cdylib files, not crates. The port maps "crate" onto "file": a cross-FILE duplicate is the flagged shape. This is a faithful approximation for the common case (one function per file pair across the project) and is documented at `index_phase`. A future schema that carries crate identity per file entry would let the port restore exact crate-granularity grouping; until then the file is the available unit.

# Detection: name-hash group plus byte confirm

`index_phase` stores, per public top-level function, a locator (`file_idx` + `node_idx`), an FNV-1a `name_hash`, and an FNV-1a `sig_hash` over the parameter type-leaf spans. `evaluate_phase` groups by `name_hash` (mirroring the in-process rule's primary by-name path) and confirms every hash match by re-reading the other record's name from its NAM source span and comparing bytes, so a hash collision can never raise a false positive. The signature hash is carried for parity with the in-process rule's signature axis and to break ties cheaply; the firing path is name-based, so a param-only signature hash (return-type position has no v1.3.0 node kind) does not change which duplicates fire.

# Full-project nam in both phases (confirmed against the ABI)

The `LintEvaluateProjectIndexVtable` doc comment states the host calls `index_phase` once with the full NAM, then calls `evaluate_phase` per file. `evaluate_phase`'s signature carries both `nam` and `file_idx`: the `file_idx` selects the file to evaluate within the full-project `nam`, which would be meaningless if `nam` were per-file. The port reads `nam` as the full-project payload in both phases; `index_phase` walks every file, `evaluate_phase` indexes `entries[file_idx]` and cross-references the project index.

# Caveat

No real NAM producer exists yet (the rust-native runner is #220, blocked by #195/#471), and the two-phase host dispatch loop is also deferred (#618 shipped the ABI surface; the host index-allocate-then-per-file loop lands with future host work). This evaluator is unit-tested against synthetic multi-file `NamNode` arrays and hand-allocated `IndexBatch` buffers, and validated end-to-end once BOTH the producer (#220) and the two-phase host loop land. The port readies the lint ahead of both, matching the schema-ahead-of-producer posture of NAM v1.1.0 (#616) and the per-file ports.

# Scope boundary: undocumented-type deferred

`undocumented-type` is the other bucket-3 lint. It is NOT in this slice: deciding whether a public item carries a doc comment needs the doc-comment text adjacent to each item, which the NAM node array does not carry today (LINE_COMMENT / BLOCK_COMMENT nodes exist as kinds, but whether a comment is a doc comment and whether it attaches to the following item is a separate inference the v1.3.0 schema does not encode). That is its own design question (does NAM gain a doc-attachment edge, or does the cdylib re-derive attachment from comment node adjacency) and its own round. Deferred explicitly.
