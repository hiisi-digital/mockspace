**Scope:** Design decisions for the no-std (token-scan) port, the variable-config-arm counterpart to round 202605282100's fixed arm.

## D1: variable config-bytes arm, length-prefixed blob

Round 202605282100 decided fixed configs cross as a `#[repr(C)]` struct and variable configs cross as a length-prefixed blob. This slice lands that blob shape for token-scan:

```
[word_boundary: u8][strip_strings: u8][strip_comments: u8][strip_doc_comments: u8]
[token_count: u32 LE]
then token_count times: [len: u32 LE][bytes...]
```

The cdylib decodes it by hand into a fixed `[(offset, len); MAX_TOKENS]` table (`MAX_TOKENS = 32`, no allocation; the largest catalogue preset lists eight tokens). Malformation (header under eight bytes, `token_count > MAX_TOKENS`, a token length running past the buffer, a zero-length token) returns `AbiStatus::InvalidArg`. Empty config (`config_len == 0`) is a no-op, same host-owns-validation rationale as file-size.

## D2: strip by skipping spans, not blanking

The in-process `token-scan` strips a length-preserving blanked copy of the source (`mockspace_rs::strip`), then scans it. A no_std / no_alloc cdylib cannot allocate that copy. Instead the port scans each token over the raw source while SKIPPING strip-spans (comments and strings, per the strip flags): a token can only match in a live run between spans.

This is faithful for every catalogue config because no catalogue token contains a comment or string delimiter byte (`/`, `"`, or a raw-string sigil), so a byte-equality match at a live position can never straddle a span boundary. The port ports the span detection of `strip` (line comments with `///`/`//!` doc distinction, nested block comments with `/** */`/`/*! */` doc distinction, plain string escapes, raw strings with `#` delimiters) and honours each strip flag independently. One deliberate narrowing: a stripped string / raw string is skipped WHOLE (its delimiters included), where the in-process strip keeps the delimiters live; no catalogue token contains those delimiter bytes, so the result is identical for every real config.

## D3: shared core, per-lint providers

token-scan backs five catalogue lints (no-std, no-alloc, no-dyn-dispatch, no-runtime-registration, no-runtime-spawn). Per task #610 R4 each lint is its own provider id with its own rule id. The shared scan logic lives in `token_scan_core(.., rule_id)`; each lint ships a thin `extern "C"` wrapper that bakes its rule id and a `ProviderExport` marker. This slice ships only `no-std`; the other four follow the same wrapper + provider shape and reuse the core (next slices, outside #615).
