# Files of a shared directory on a ref

The topic of 6 November (`202611060850/202611060850_topic.mock-directory-in-custom-refs.md`) put a whole directory of the mock directory on a ref, one ref to one directory, and refused `design_rounds` outright. This one amends it in two places and says why.

## What changed above it

The earlier topic took a default from the 3 November answers: design templates keep their place beside the code for now. Op has since said what the branch tree is to hold, on 11 November:

> Idea is, whatever is left on the actual public branch tree, is simply what we now have in crates for source, but without the md.tmpl files outside of its readme one and that's the generated one and not the tmpl one.

The intent in that is the shape of the branch tree: the sources of the crates, and a generated readme, and no template. The earlier default is superseded by it. Templates therefore leave the tree, and they sit in the same directories as the sources that stay, so a ref has to be able to hold some files of a directory and leave the rest to the branch.

## A ref that holds files by pattern

A `[[data_ref]]` may carry `include`, a list of patterns relative to its `path`. `*` stands for any run of characters inside one name and `**` for any number of whole directories. Nothing else is special, and a character git's exclude file would read as special is refused, so one pattern has one meaning. Such a ref holds the files its patterns match and no other file of the directory.

The instance of such a ref lies among the branch's files, so it takes no `instance` of its own, and it never reads, writes, removes or excludes a file its patterns do not match. What it refuses, before it writes anything:

- a tip or a base that holds a file the patterns do not match, since that file would be written among the branch's and no later edit could name it, and under narrowed patterns it would read as removed;
- a write or a removal below a symlink, which would go to wherever the link points;
- an update where anything on disk, the branch's or the instance's, stands in the way of a file of the tip.

The exclude file gets each pattern and, after it, the line that takes directories back out of the pattern, since an exclude pattern matches a directory too and an excluded directory is never looked into.

## The closed rounds

`design_rounds` was refused as a `path` because the open round's flat files are part of the branch they are written on. The closed rounds are directories and belong to no branch. A ref may now take `design_rounds` with patterns that reach only into a directory (`*/**`), and a pattern that could match a flat file is refused where it is declared. The round model itself does not change.

## What stops a run

A declared ref with no instance in a clone reads as a directory with nothing in it, and a lint over it passes for the wrong reason. Every command but `data-refs` and the recovery ones stops first on a declared ref with no instance, on an instance none of whose files are on disk (a clean of the work tree takes the files and leaves the record; `data-refs restore` writes them again from the commit the instance was at), and on a file a ref holds that the branch still tracks.

## Pairing

A landing names the data it was gated against with one `Mock-Ref` line for each declared ref. A ref is named in that line by its namespace, and one check, the store's own, decides what a namespace is for both. A ref not born yet has no commit to name, so a landing gated against it says so in its line, `Mock-Ref: <namespace> unborn`, and the pairing takes that line as the gate wrote it, as it takes a line that names a commit. A landing is held to a line for each ref its own tree declares, so one made before a ref was declared needs none for it; a landing whose tree has no config that can be read is held to every ref declared now. No clock decides any of it: the time of a landing made on one machine is never set against the time of a commit made on another, since a clock that is off would let a landing with no line through. A line missing from any other landing is refused as before.

## One ref for the whole mock directory

A ref may take the mock directory itself, `path = "."`. It then has to carry patterns, since a ref holding every file of the mock directory would hold the config that declares it, and each pattern has to name where it reaches: one that starts with a wildcard, one that could hold the config, one under a directory that has a store of its own (the registry, the test history) and one that could hold a flat file of the open round are each refused where they are declared. Such a ref lies around every other declared ref, and two refs do not nest, so no other `[[data_ref]]` is declared beside it. What a project keeps off its branch then goes to the one ref.

## What the gates see

Git tracks none of the files a ref holds, so a gate that asks git what changed hears nothing of them. The phase gates are therefore told two lists by the engine, the files the declared refs hold and which of those differ from the commit their instance is at, and judge a held file by the second list as they judge a tracked file by the diff. A template that moved to a ref is still a document to the gates, and the removal of it from the branch is not read as a change to it.

`data-refs commit` runs the lints of the repo first and commits nothing where they fail, since the commit of a ref passes through no commit hook of the branch.

The pre-push hook is a branch's gate. The store names the ref it pushes in `MOCKSPACE_DATA_REF`, and the hook stands down for a push where every ref pushed is the one named. A branch pushed beside it is gated as before. Setting the variable by hand skips the hook as `--no-verify` does.

## Named migrations

A tree is moved from one shape to another by `cargo mock migrate <name>`, and every call names the migration it means. A migration checks that the tree is the one it was written for and refuses any other with the reason, its dry run prints every path it would touch, and it takes what it is to move from its arguments and infers nothing. A run that was stopped part way is finished by the same call, which makes the steps that are missing: a ref that was made and whose directory was never recorded is taken as the instance where the directory still holds exactly the files of the ref. A migration already made is refused. `directory-to-ref` moves tracked files of the mock directory to a data ref; `round-filenames` renames the round files of the older naming.

## Migrating references

`references-to-letkajenkka` is a named migration, and it keeps to the rules above. It reads the templates the repository lists (the files git tracks, and the ones not yet added and not ignored, never a walk of the directory tree), the files the declared data refs hold, the registry as the loader reads it, and every file the loaders read for the preset shorthands of `[lints.<name>]`: `lints.toml`, `mock/lints.toml` and `mockspace.toml`, an `extends` that is an array item by item. A declared data ref with no instance in the clone is refused with `data-refs instantiate` as the way out, since a run that skipped it would call the tree migrated with its files untouched. Where a file of an instance was rewritten, the run says to commit it with `data-refs commit`, because committing the branch does not carry it. A tree with nothing left to rewrite is refused as already migrated, naming what it could not rewrite, and a run stopped part way is finished by the same call. A file a `.gitignore` keeps out is not held and not read: git lists no such template, and a data ref holds no such file. A file to rewrite that is a symlink, or lies below one, is refused before anything is written, since the write would go to wherever the link points, as a data ref refuses a write below a symlink.

## What an instance reads

A ref holds the files its patterns match, less what a `.gitignore` of the work tree keeps out, as the branch would. A file a `.gitignore` matches is never read into an edit, so never committed, and never removed or written by the engine; `status` names each one inside an instance on a line of its own (`ignored, not held: <path>`, a directory git ignores whole as one line with a trailing `/`), and `directory-to-ref` names the same files in its dry run and its real run, as files it leaves where they are. The rules are git's own, read by `git ls-files` from the instance, so a `.gitignore` above the instance counts as one inside it does. The repository's `info/exclude` and `core.excludesFile` are not read: the first carries the line that hides the instance itself, and the second is one person's and not the repository's. A file the ref already holds stays held when a `.gitignore` matches it later, as a tracked file stays tracked in git. An instance outside every work tree has no `.gitignore` git would read, and none applies there.

The other thing an instance does not read is a cache directory, a directory that carries a `CACHEDIR.TAG` with the signature of the cache directory tag specification, which cargo writes into every `target`. A build's output is not data, a file under one never reaches the ref, and the directory is not named as ignored, since nobody means it as data; where the ref already holds a file under that directory, it is read as the rest is.

Where `core.fileMode` is off the executable bit of a file on disk means nothing, and the bit is the one the ref holds for that path, so a mount that reports every file executable reads no file as changed and a commit never sets the bit. A new file is then not executable.

A file is read as it was when it was last hashed where its size, modification time, change time and inode are what they were then and the file was already older than a margin of two seconds at that time, which is the rule of git's own index. The record of those stamps sits beside the instance's record and is only ever a shortcut: where it is missing, damaged or unwritable the file is read again. A write that follows the hashing has a modification time no earlier than the hashing, and a program that puts the modification time back cannot put the change time back. What this does not hold on is a clock that moves backwards across the margin, and a filesystem that keeps neither time.

A declared ref the remote does not have yet is a ref not born yet. `instantiate` on it, once the remote has been asked and answered that it has none, makes the directory if it is absent and writes an instance record whose base is no commit, and succeeds; the standing gate takes that instance, and `verify` reads it as clean while the ref has no tip. The first `commit` builds its edit on no commit and makes the ref. A second clone that did the same has its push rejected, fetches, and meets the edit through the merge hook as for any concurrent commit, so neither clone's file is lost; `update` then brings the first clone's files into its directory. A namespace no `[[data_ref]]` declares is refused by `instantiate` as before: only a declaration makes a ref that is not born yet.

## What git may write over, and the copy of the files

The files of an instance are hidden from the branch, and git treats a hidden file as expendable. The sparse checkout keeps a checkout, a switch, a forced checkout and a hard reset to a commit from before the migration from writing over an edited instance file, and the managed block it carries is written from the same lines as the exclude file, so the two cannot disagree about which paths are the instance's: an exclude line with its negation toggled is a sparse line. The block follows the declarations, and one that names a ref no longer declared is taken out by `instantiate` and named by `verify`. Per-worktree config is turned on for the block, and where the common config carries `core.bare` or `core.worktree` they move into the config of the main worktree alone first, as `git sparse-checkout init` does, so the linked worktrees of a bare clone keep working. Where the sparse checkout was off, the file is started from `/*` and the block, since lines an earlier sparse checkout left there are nobody's patterns now and would take away the branch's files they leave out; where it was in cone mode, it is switched to the full pattern mode the block needs, and that is said, since the person's own lines are read another way from then on.

What the sparse checkout does not stop: a merge of a branch cut before a migration, where that branch edited a path the migration took off the branch, writes the branch's bytes whatever the patterns say, and a reset back from a commit from before the migration removes every file of the instance that commit tracked. So each instance keeps a copy of its files in a local ref, `refs/mock-backup/<namespace>`, under a directory named by its record, one commit for each distinct state and never pushed. The copy has three parts. The files edited against the base are copied whenever the engine looks at the instance. Every file of the instance is kept as it is from a `reference-transaction` hook, which runs `data-refs snapshot` when git moves `ORIG_HEAD`, as a merge, a rebase and a reset do; a merge and a rebase move it before they write the work tree, and a reset after, so for a reset the copy that counts is the one the command before it took. And the next look takes a file of that guard which is gone, or which holds bytes the object database already had (bytes a commit brought, where an edit made since is new bytes), for one git wrote over, and keeps the bytes from before. Git writes a file through the filters its attributes name (`eol=crlf`, `ident`, a filter driver such as LFS), so the bytes on disk are asked of the database twice: as they are, and hashed again as git would store them, from the top of the work tree so the attributes of the path apply. A filter that fails leaves the file to the first answer.

A file git wrote over is said by `status`, with the two ways on, until it holds those bytes again: `data-refs restore <namespace> <path>` writes them back, after the bytes on disk are copied as an edit, and refuses, writing nothing, where that copy cannot be made, since the bytes on disk would then be in no copy and no file; `commit` refuses to push the bytes on disk without `--accept-overwritten`, which takes them and ends the warning. An edit made after the git command and before the next engine command is new bytes, and is not taken for git's, with one exception: where the guard held an edit and the branch's index holds the path as only git puts it there (unmerged, or tracked without the skip-worktree bit the sparse checkout gives every path of an instance), git wrote that path, and the edit the guard held is kept as written over though the file has been edited again since. One that puts back bytes a commit or an earlier copy holds is taken for git's too, and `--accept-overwritten` is the way past it.

The hook never stops the person's git command: it exits 0 whatever the launcher does, an engine that does not know `snapshot` included, and says a failure on stderr. It is the repository's own, in `<git-common-dir>/hooks`, which no other repository reads, and it is never written over a hook of the person's, which `verify` names instead. Where `core.hooksPath` points at the gate's durable directory, the gate's `reference-transaction` there hands over to it, finding the repository's git directory from what git gives a hook, a linked worktree's included, without starting a program, since it runs on every move of a reference in every repository that points there. Where git-shook dispatches, the same hook is one of the gate's entries. The gate's directory is made again by every engine run, so a version bump or a clean of the build leaves the hand-over in place by the next command, and `verify` names a `core.hooksPath` that would not reach the hook.

The copy is written by a compare-and-swap of the backup ref, re-read and built again on a lost race up to eight times, so two worktrees copying at once both keep theirs. The hook runs inside the transaction that moves `ORIG_HEAD`, in its `prepared` state, with that transaction's locks held. The files backend locks each ref apart, so the backup ref is free then. The reftable backend locks the whole stack the transaction writes to: in git 2.47, `refs/reftable-backend.c` takes `tables.list.lock` in `reftable_be_transaction_prepare` through `reftable_stack_init_addition` in `reftable/stack.c`, waiting `reftable.lockTimeout` (100 ms by default), and lets it go only when the transaction is committed, after `refs.c` has run the `prepared` hook. The stack of the repository holds the backup ref, and `ORIG_HEAD` too in the main worktree, so a write of the backup ref from the hook fails there every time. A guard is therefore made as objects, which take no lock, and where the ref will not take it, the commit that holds it is named in a file beside the instance's record; the next look takes that commit for the last copy and folds it into the ref as the second parent of the next commit there. Under the reftable backend a guard goes there at once, since each attempt at the ref would cost the person's git command the lock timeout; under the files backend only after the eight attempts. Until the next engine command the objects are named by nothing git reads, and a `git gc` prunes such an object only once it is older than `gc.pruneExpire`, two weeks by default. The git this was built against (2.43) has no reftable backend, so the test under it runs only where git can move a repository to one (`git refs migrate`, 2.46 and later), and says it was skipped elsewhere; the same path is tested under the files backend by holding the backup ref's lock across a merge. A copy that cannot be written is said and fails no command that only reads, and `commit` goes on past it; a copy that cannot be read fails `commit`, since what git wrote over is then not known. One case of it has a way past, provisional until it is ruled on (question ticket `the_way_past_a_copy_a_git_gc_pruned_is_provisional`): a copy named only beside the record whose commit a `git gc` pruned before the next engine command is lost, every look and `commit` say so, and `commit --accept-overwritten` forgets that copy and takes the bytes on disk, so the copies go on from the backup ref. The stamps of the instance's files make the copy of an unchanged edit cost no hashing, and only bytes neither the base nor the last copy holds are written to the object database.

A write git makes over an edit no copy holds yet is the window that stays open: `git cherry-pick` of an old commit and a command that names the path, with no engine command since the edit, and a reset back from a commit from before the migration over an edit made while the branch sat at that commit, which then tracked the file, as git's reset drops the edit of any tracked file. And an edit git wrote over that the person took off the branch's index (`git rm --cached`) and edited again before any engine command: nothing git left says it wrote there, the file holds new bytes, and the edit from before is kept only in the history of the backup ref. Each is pinned by a test, so the day git closes it the test says so. A launcher that hangs hangs the git command with it, since the hook waits for it.

The ids an instance carries are typed, an object id, a file's blob and mode, and a base that is a commit or none, so nothing but the hex of an object reaches git where an object is meant.

## Interrupted commands

A `commit` or an `update` that stops part way, by a failure of git at any step, leaves every file of the instance as it was or as the tip has it, records nothing, and is repeated by the same command. Where the push of a commit landed and the local ref was not moved after it, the instance is behind its own commit, and `commit` names `update` as the way on.
