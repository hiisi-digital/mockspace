# One pass, shared by every lint

A lint run reads the repository once, every lint works from that one reading, the lints run at the same time, and a lint whose inputs did not move is not run again. This topic says what that reading is, how a lint asks it, what is kept between runs, and where a copy is accepted.

## What asked for it

Op, in the brief of the work, on why kaski's gate is slow:

> I am almost entirely sure this requires a lot of optimisationsnupstream on mockspace minting harness and framework, caching, sharing data collected between all lints, so ideally only one pass through everything runs, no more, and all lints work from the same shared result without copies or clones as much as they can, but still allowing parallelism so some amount has to be accepted.

The intent is four things: one pass over the tree and no second, one shared result every lint borrows from, the lints in parallel, and a cache so that what did not change is not judged again. The rest is kept for provenance. He also asked that viola be benched first as it stands, since a clear win there would have meant porting the gate onto it:

> They should evaluate whether adopting current viola and writing its rust extension might be simply more performant as is. It's deno though so not ideal. But worth benching vs current rust mocksoace one. If it's a clear win without any changes, perhaps the biggest thing we can do is port the linter to be viola.

It was benched in kaski (`mock/benches/lint-viola/FINDINGS.md` there, at `cb08294e37`): over kaski's whole tree viola's default lints take 293 s where mockspace's lints of the same kind take 5.9 s. So the gate stays in mockspace and this is the design of its harness.

## What a run costs now

Measured in kaski (`mock/benches/lint-run/FINDINGS.md` and `mock/research/202611121428_the-lint-run-measured/NOTES.md` there): 76.6 s with every lint run, 35.1 s over warm verdicts, 1.8 s of either the engine's start. Every lint runs after the one before it on one thread of four. The engine shares one read of a crate's sources and one parse of each file between the crate lints, which is 3.1 s of the run; the rest is lints that walk, read and parse for themselves, some 60 reads of a file, 47 started commands, 15 parsers and a dozen walks written out across the three sets of lints, so one run opens each file of the tree a little over four times and starts 648 processes, 515 of them `git`.

The saved verdicts that exist key a crate lint on a reach the lint declares (`Reach`), and leave a repo lint to run every time unless it splits itself by hand with `remembered` and lists the bytes each part depends on. A part left out replays a stale verdict as a fresh one, and nothing checks the list.

## The one reading

A run lists each directory of the repository at most once, when a lint first asks what is in it, and what the listing gave (the names, the sizes, the times) is what every later asker gets. Everything else is taken the same way, when a lint first asks, and kept for whoever asks next: a file's text, read once; a Rust file's syntax tree, parsed once; a manifest or any other TOML file, parsed once; the answer of a `git` question, asked once; the output of any other command over inputs the lint names, run once. The registry, the crates and their graph are in it as they are handed over now.

Nothing is read ahead of being asked for, since a commit that touches one crate should not pay for reading the rest. Once is what the reading promises, to every lint and every thread: two lints that ask for the same file at the same moment get the same text, read by one of them.

A lint borrows. What it is handed is a reference into the reading, text as `&str`, a tree as `&Tree`, a list as a slice, and the reading outlives every lint of the run. A crate lint's context is built from the same reading, so the sources it has always been handed are these and not a second copy read for it.

## How a lint asks

A lint is handed a view of the reading that is its own, and every question it puts goes through the view: the files under a directory or matching a glob, a file's text or bytes, a parsed file, a `git` answer, a command's output. The view writes down each question with a digest of the answer. That list is the lint's trace for the unit it was judging, a crate lint for one crate or one file, a workspace lint for the crates, a repo lint for the repository.

The trace replaces the reach a lint declared. A lint no longer promises what it reads, it is seen reading. A listing is part of it, so a lint that walks a directory is run again when a file appears there, and not only when one it read changes.

A lint that spends its time on separable items, a shader compiled each, a file checked against a table, splits itself as before, and each item now has its own view and its own trace in place of a list of bytes written by hand. The items run at the same time.

What a lint reads outside its view is not in its trace, so a lint that opens a file or starts a command for itself is one the cache cannot answer for. Every lint mockspace ships and every lint of the packs moves onto the view, and a check over a pack's sources refuses a lint that reaches the file system or starts a process on its own, so the next one written does not bring it back.

## What is kept between runs

For each unit, the trace and the findings, under the lint's identity and its configuration. On the next run the unit's trace is asked again, each question against the reading, and where every answer has the digest it had, the findings are replayed and the lint does not run. Asking a trace again is cheap by the same sharing: a file whose size and time did not move has the digest kept for it, a listing is taken once, a `git` answer is asked once for every lint that wants it.

So what a commit runs follows from what it changed. A lint whose trace holds no file the commit touched, no listing it added to or took from and no answer it moved, is replayed; a lint that read a touched file runs, and so does one that reads what a touched file feeds, since that is in its trace too. Nothing is declared for this and no list of globs is kept. The full run stays one command, with the store off, and it finds what the cached run finds; a test over a real tree holds the two to the same findings.

The store is keyed on content. The file's time is only how a digest already taken is found again; a file put back to what it was has the digest it had.

## In parallel

The units of a run are put on the machine's threads, longest first by what each took the last time. The findings are gathered and printed in the order the run has always printed them, so the output does not depend on which thread finished first.

A lint is shared between threads, so a lint holds no state it changes while judging. The traits say so (`Send` and `Sync`), and a lint that kept a parser or a cache in a cell takes it from the reading instead.

## Where a copy is accepted

- A finding is owned by whoever made it and moved to the run. It was a copy before and it stays one.
- Each thread has its own parser and its own query cursor, since neither can be shared. The trees they make are in the reading, once.
- A trace holds digests and names, not contents.
- A command's output and a `git` answer are kept as the bytes the process wrote, once, and lints borrow them.

Nothing else is copied. A file's text is held once for the run, and a lint that wants a part of it holds a slice.

## What goes

The declared reach and its check, the two `remembered` forms and the plan of touched globs go, with the code that keyed crate verdicts on them, since the trace does what each of them did and the old way is not kept beside the new. A pack written against them is moved in the same work: mockspace's own lints, `mockspace-extra-lints` and kaski's.

## What is not in this

The registry gate and the pack's identity are phases of the engine and not lints; they are 4.4 s of a warm run in kaski and are left as they are here. The launcher's start, 1.8 s, is also outside it.

## Decided while building

These were settled while the reading was built and are recorded here because the sections above do not name them.

A lint that depends on something a trace cannot hold, an environment variable, the clock, a file it has to open itself, says so by calling `untraced` on its view. The unit is then never saved and is judged on every run, and so is every item of an `each` it asks after the mark: an item inherits it, is never replayed and is saved for nobody. An `each` running when the mark is made saves none of its items. Items saved by an `each` that ended before the mark stay saved, since they were judged on their own traces alone. Nothing else lets a lint read past its view.

The guard that keeps lints on their view, `lints-read-through-the-view`, refuses `std::fs`, `std::process`, `std::env`, the crates that walk a disk or a repository, a `Reading` of the lint's own and the path methods that ask the disk with no argument. It leaves alone four things, and only these. Test code builds its fixtures on disk and may. A file under a directory named `tools` is a tool's, which keeps no unit and may read anything. A `Reading` type the file declares itself is not the engine's. An entry of a listing answers `is_dir` and `is_file` from the listing, and is asked as `Entry::is_dir(entry)`, since without types the guard cannot tell an entry from a path. The `untraced` call exempts the reads after it in its function only when it is a statement of its own at the top of the body, so it runs whenever they do; one in a branch, a closure or a nested block, or one after the read, exempts nothing. A read inside the closure of an `each` asked after the mark is exempt too, since every item of that call carries the mark.

An item of `each` is saved under what names it from one run to the next, its `Item::key`. Strings and paths are items, and a pair is not: it would be keyed on one half and replay the other. Whatever the judging takes from outside the item and its view, a table, a setting, a value worked out before the call, belongs in the key.

The key also holds where the call is made from, its file, line and column, and how many calls the unit made from that place before it. An ordinal of calls alone handed the items of a call skipped on one run to the next call. A helper that calls `each` for others is one place for all of its callers unless it passes the caller's place on, and its calls are then told apart only by their count, so such a helper either passes the place on or puts what tells its calls apart in the key. A question put to the unit's own view while its items are judged belongs to no item, so the items of that call are not saved; this holds for every such question in the call, an `each` asked from inside an item among them.
