# Topic: one record, and every writer a projection

**Date:** 2026-08-15
**Phase:** TOPIC
**Scope:** `bench-harness/src/harness.rs`, `history.rs`, `sample.rs`, `report.rs`, `driver/`, `bench-core/src/lib.rs`
**Source:** the metadata inventory on `docs/bench-ergonomics-survey`, ratified in shape by op

The framework writes data in seven places and no two agree on what a run is. This topic settles the
shared base and the rule that keeps it one.

## The inventory

| writer | omits, that another carries |
|---|---|
| samples CSV | all identity (bench, sweep and point live only in the filename), seed, environment, config |
| `.meta.json` | identity, seed, timing knobs, arms |
| history TSV (`schema_v1`) | build profile, environment, toolchain, seed, dylib hashes, verdicts |
| report | seed, identity as data, config |
| `INDEX.md` | everything but its columns; regenerated |
| `.bench_cache` | nothing else knows the dylib hash, and it knows nothing else |
| `results/void/<runid>/` | the runid appears in no other artifact, so nothing ties a run together |

**What nothing carries at all**: cell identity as data, the resolved seed, the effective timing
knobs, declared-against-measured arms with drop reasons, per-arm dylib hashes and dep pins, the
effective build profile, a run identifier, and any verdict. Every verdict in the system is printed
to stderr and recorded nowhere.

**And one field lies.** `build_profile` in `.meta.json` is a hardcoded literal
(`harness.rs:50-55`). On `dev` it happens to be accurate. The moment the `[build]` overrides on the
open PR land, it records a profile that was not used. That field was added by the coordinator
earlier in this arc, and it is the exact defect class this round exists to close.

## The shape, ratified

**One `CellRecord`, written once, where the analysis already runs.** The driver's post-cell block is
the only place that today feeds the CSV, the report, the history and the summary, so it is the
centralisation point.

The record replaces `.meta.json` at the same path as a superset, so nothing breaks. Sections:
**identity** (bench, sweep, point, manifest key, title, runid), **config** (resolved seed, workload,
effective timing knobs, flags, roles, declared arms), **build** (profile values from the arguments
actually passed rather than a constant, the dep spec, per-arm dylib hash from the hasher
`.bench_cache` already owns), **environment** (today's fields plus framework version), **execution**
(arms measured, arms dropped with reasons, disasm result, hook verdicts), **analysis** (per-arm
median and CI, regression flags).

**The rule that makes it a base rather than a bolt-on: every other writer is a projection of the
record, and no writer invents a field.** History rows become a fixed projection under a
`schema_v2` carrying runid and build columns, with old files readable as v1. `INDEX.md` renders from
records. The report header cites its record. stderr prints from it.

## What this settles that was otherwise a separate argument

A failing gate withholding its history append stops being a behaviour question and becomes a stated
**projection policy**: the record exists whatever the verdict was, so nothing is lost, and the
policy says a failed cell projects no history row. The build-profile asymmetry closes the same way,
because the profile is in the record from the arguments that were passed and the history projection
carries it, so a profile change stops reading as an unexplained regression.

## What this topic must settle

- The record's exact fields, and which are required rather than optional, since an optional identity
  field is the same defect one level up.
- Whether `schema_v2` is a migration or an additive column set, and what reads v1 rows afterwards.
- What happens to `.bench_cache`, which currently holds the only copy of a fact the record needs.
- Whether the runid is per invocation or per cell, and what it ties together.
- Whether a record is written for a cell that failed before measuring, which decides whether the
  record is a log of attempts or of results.

## What is not in scope here

The validation semantics themselves, which have their own topic file. This topic takes whatever that
one decides and gives the verdict a home; it must not settle the verdict's meaning by choosing where
it is stored.
