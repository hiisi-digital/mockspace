## D2: NamNode tree navigation [LOAD-BEARING]

The `NamNode` carries `kind`, `parent`, `first_child`, and byte/row spans. There is NO next-sibling pointer. So a node's children are found by scanning the array for nodes whose `parent` equals that node's index (O(n) per parent, O(n*items) per file; fine for source files). The SOURCE_FILE root is the node with `kind == SOURCE_FILE`; top-level items are its direct children.

**Op-confirmation / future axis**: if profiling shows the parent-scan navigation is too costly on large files, a `next_sibling` field is the natural NamNode v1.2 addition. Not needed for the item-count metrics; recorded as the escalation path.

## D3: identifier / keyword inspection via source byte spans [LOAD-BEARING]

The flat node array carries structural kinds plus byte spans, NOT identifier text. To inspect a token (e.g. is a visibility modifier exactly `pub` vs `pub(crate)`), the cdylib reads `source[node.start_byte .. node.end_byte]` from the `NamFileEntry.source` bytes and compares. This avoids growing the canonical `node_kind` table with text-bearing kinds for every keyword, and reuses data the NAM already carries.

For PubItemCount: an item is public iff it has a child VISIBILITY_MODIFIER node whose source span is exactly `pub` (matching syn `Visibility::Public`; `pub(crate)` and friends are `Visibility::Restricted`, not public). PrivateItemCount is TotalItemCount minus PubItemCount, matching `file_metric`'s `count_items(!is_pub_item)`. The item-kind classification mirrors syn breadth (`is_item_kind`) and the narrower pub-eligible set (`is_pub_item_kind`: fn, struct, enum, trait, type, const, static, mod).

## D4: what this slice does NOT port, and why

- The `ast-type-position` and `ast-node-position` lints need node kinds not in #616's 19-kind table: `call_expression`, `field_expression` (node-position), and finer type-node granularity (type-position detects e.g. `u8` in a field type). Per #616 the `node_kind` table is append-only and grows in later schema sub-versions, so these lints are blocked on a viola-side `node_kind` append (a separate cross-repo slice). The source-span text approach (D3) can cover identifier text, but the STRUCTURAL kinds (which node IS a field type) must come from the producer.
- No real NAM node producer exists yet (the rust-native runner, #220), so all bucket-2 cdylibs are unit-tested against synthetic node arrays now and validated end-to-end once #220 lands. This matches #616 shipping the schema ahead of its producer.
