# Merging

Merges here are automated as far as git can be taught to do them, and judged by what they add rather than by what they touch. Three parts: the files that merge by a driver, the files that only grow, and a merge commit inside a design round.

## Files that merge by a driver

`cargo mock` writes the `.gitattributes` lines and registers each driver in the clone, so a merge touching these reports no conflict.

- **Generated documents.** The top level of `docs/` goes to the `mockspace-generated` driver. It keeps this side's copy of a generated file (read from its header, or from the diagram beside a rendered image) and merges any other file in `docs/` as git does, but only where the hook that regenerates afterwards is installed: `post-merge` for a merge, `post-rewrite` for a rebase, found with `git rev-parse --git-path hooks/<name>`, and generated under `<mock>/target/hooks`, so a fresh worktree needs one `cargo mock` first. A rebase's replayed commits may carry the upstream's copy; the tip does not. The regeneration is a follow-up commit (`chore: regenerate generated files after merge`, or `after rebase`) or, for a merge that stopped, part of the commit that concludes it. The `generated_files_*` tests enforce this.
- **Registry rows.** Merged by `[[namespace]]` and `id`: additions on both sides stay, only a row changed two ways conflicts.
- **Test history and closed rounds.** The `test-history` skill and the round id check carry their own merge drivers.

A cherry-pick, revert, `git am`, `git checkout -m` or stash application regenerates nothing, so a generated file conflicts there: regenerate with `cargo mock` once the sources are resolved, never pick a side.

## Files that only grow

A list of `mod` lines, a table of strings, a log of known gaps: each changes by someone adding to it and by nobody touching what is already there. `.gitattributes` sends these to the `mockspace-append` merge driver, which `cargo mock` registers in the clone and which runs `cargo mock merge-additions`.

- **Neither side changed or removed a line of the base**: both sides' additions stay, each in the spot it was made in. Where both added at one spot, ours comes first and theirs after it, each in its own order.
- **Either side edited or removed a base line**, or both added one of the same lines at one spot, or the file has no base or no final newline: the file is merged as text, with git's own markers and exit status. The driver never selects a side.
- **The same line added at two different spots stays at both**, which is what git's own merge does with it.

Mockspace names each source package's `SHAME.md.tmpl` and `BACKLOG.md.tmpl`. A project names the rest in `mockspace.toml`:

```toml
append_only = ["content/strings/en.toml", "{mock_dir}/crates/*/src/tests/mod.rs"]
```

Each entry is a `.gitattributes` pattern relative to the repository root, as narrow as the file it names. A directory is not an entry: a file in it that is not append-shaped would be handed to a driver that leaves it to git, which is safe, but the line then claims more than is true. Run `cargo mock` once and the lines and the driver are written; an entry taken out of the list takes its line out of `.gitattributes` on the next run.

A file that is regenerated by a tool (a results index the bench driver rewrites, a lockfile) is not append-only: its base lines change on every run. It is regenerated after the merge.

## A merge inside a design round

The phase gates judge what somebody wrote. A merge commit is judged by what it adds beyond its parents, per staged file:

- a file byte-identical to one parent, or to what git's own three-way merge produces, adds nothing;
- a conflict settled by keeping lines of both sides adds nothing, when every staged line is a line some parent carries, no line appears more often than the parents carry it together, every line all the parents carry is still there as often as the parent with the fewest, and the sides keep their own order;
- a line neither parent has, a line repeated beyond the parents, a line every parent has that is gone, or two lines of one parent traded places, is an edit and is gated as one.

So `git merge <trunk>` is committed once, in whatever phase the round is in, designs and source together. Resolve a conflict by consolidating both sides and keep no line you wrote yourself in the merge commit: a new line goes into its own commit, in the phase that permits it. Committing the merged designs in DOC, the source in IMPL and merging again is not needed and not done.

The sides' sections go one after the other, in either order, each in its own order: that keeps both as new sections and moves neither. The order test is a greedy longest-common-subsequence split, so a rare consolidation that only another split explains is refused, which is the safe direction. It runs for up to four parents and a table of four million cells; past either only the counts apply. An octopus is covered by the line tests and not by the three-way reproduction, which wants a single merge base.
