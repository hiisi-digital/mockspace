# Merging

Merges here are automated as far as git can be taught to do them, and judged by what they add rather than by what they touch. Three parts: the files that merge by a driver, the files that only grow, and a merge commit inside a design round.

## Files that only grow

A list of `mod` lines, a table of strings, a log of known gaps: each changes by someone adding to it and by nobody touching what is already there. `.gitattributes` sends these to the `mockspace-append` merge driver, which `cargo mock` registers in the clone and which runs `cargo mock merge-append`.

- **Neither side changed or removed a line of the base**: both sides' additions stay, each in the spot it was made in. Where both added at one spot, ours comes first and theirs after it, each in its own order.
- **Either side edited or removed a base line**, or both added one of the same lines at one spot, or the file has no base or no final newline: the file is merged as text, with git's own markers and exit status. The driver never selects a side.

Mockspace names each source package's `SHAME.md.tmpl` and `BACKLOG.md.tmpl`. A project names the rest in `mockspace.toml`:

```toml
append_only = ["content/strings/en.toml", "{mock_dir}/crates/*/src/tests/mod.rs"]
```

Each entry is a `.gitattributes` pattern relative to the repository root, as narrow as the file it names. A directory is not an entry: a file in it that is not append-shaped would be handed to a driver that leaves it to git, which is safe, but the line then claims more than is true. Run `cargo mock` once and the lines and the driver are written.

A file that is regenerated by a tool (a results index the bench driver rewrites, a lockfile) is not append-only: its base lines change on every run. It is regenerated after the merge.

## A merge inside a design round

The phase gates judge what somebody wrote. A merge commit is judged by what it adds beyond its parents, per staged file:

- a file byte-identical to one parent, or to what git's own three-way merge produces, adds nothing;
- a conflict settled by keeping lines of both sides adds nothing, when every staged line is a line some parent carries and every line all the parents carry is still there;
- a line neither parent has, or a line every parent has that is gone, is an edit and is gated as one.

So `git merge <trunk>` is committed once, in whatever phase the round is in, designs and source together. Resolve a conflict by consolidating both sides and keep no line you wrote yourself in the merge commit: a new line goes into its own commit, in the phase that permits it. Committing the merged designs in DOC, the source in IMPL and merging again is not needed and not done.

The test is on a set of lines, not a sequence. Reordering what the parents wrote passes; typing a new line does not. An octopus is covered by the line test and not by the three-way reproduction, which wants a single merge base.
